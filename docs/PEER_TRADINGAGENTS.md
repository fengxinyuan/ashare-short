# 同类项目机制对照：TradingAgents-CN

> 对照对象：`/root/TradingAgents-CN`（v1.1.0，`hsliuping/TradingAgents-CN`，
> TauricResearch/TradingAgents 的中文增强版）。
>
> ⚠️ **许可证先看清楚**：该项目是混合许可证——`app/`（FastAPI 后端）与
> `frontend/`（Vue 前端）是**专有目录，商业使用需授权**；其余部分 Apache 2.0 但
> 同样附商业使用限制条款。**参考思路没问题，拷贝代码前必须先读 `LICENSE` 与
> `COPYRIGHT.md`。** 本文只做机制对照，不含代码搬运。

## 1. 定位差异（决定了什么能借、什么不能）

| | TradingAgents-CN | 本系统 |
|---|---|---|
| 任务 | **单票深度分析**：给定一只票，跑一轮多角色分析产出买卖建议 | **全市场日周期**：盘前筛选 → 盘中监控 → 盘后台账 |
| 周期 | 通用，不限持有期 | 超短（隔夜至 3 日） |
| 编排 | LangGraph 状态图，多轮辩论 | 确定性流水线 + 单轮辩论 |
| 数字来源 | LLM 读数据产出报告 | **只在确定性层产生**，LLM 不得产出数字 |

因为任务不同，**能借的是机制，不是流水线**。它没有选股环节，本系统没有多轮辩论
环节，两边的主链路不可互换。

## 2. 它的角色链

```text
5 个分析师（技术面 / 基本面 / 新闻 / 社媒情绪 / 中国市场特化）
        ↓ 各产出一份报告
多空辩论：Bull Researcher ⇄ Bear Researcher（N 轮）
        ↓
Research Manager 裁决  →  投资计划
        ↓
Trader  →  具体交易决策
        ↓
风险三方辩论：激进 ⇄ 保守 ⇄ 中性（N 轮）
        ↓
Risk Manager 裁决  →  最终决策
        ↓
Reflector：按兑现结果反思，写入各角色的向量记忆库
```

本系统已有的对应物：

- **5 分析师** ≈ `agents/collectors.py`（市场舆情 / 个股舆情 / 板块动量 / 个股日线 /
  个股分时 / 五档盘口）。**但本系统这一层不含模型**——数字全在确定性层产生。这是
  本系统更严的地方，不该向它靠拢，理由见 §5。
- **多空辩论** ≈ `agents/debate.py`（多头举证 / 空头举证 / 裁判指出分歧点）。机制
  同构，但本系统是**单轮**（每天 3 次调用），它是 N 轮可配。

---

## 3. 三个值得借的

### 3.1 风险三方辩论（最值得借）

**它做对的事：把辩论分成两层。**

- **方向层**（Bull ⇄ Bear）：这只票会不会涨。
- **风险层**（激进 ⇄ 保守 ⇄ 中性）：辩的不是方向，而是**交易员给的这个仓位、这个
  止损、这个入场点合不合理**。保守方的 prompt 明确要求「积极反驳激进和中性分析师
  的论点，指出决策可能使公司面临不当风险的地方」。

**本系统只有方向层。** 风险话不是没有，而是散落成了**规则写死的固定句**：

- `_check_breakout`：「突破买的止损在突破位下方，距离通常大于回踩买——仓位按此折算」
- `_check_reversal`：「逆势买入：仓位减半，目标只看前高的一半」
- `_check_range_low`：「震荡市买法，目标锁区间上沿——不按趋势票的持有期拿」

这些句子每次都一样，没有对抗过程，也不随当日读数变化。

**建议的轻量落法：不必上三个 LLM 角色。** 先做成**确定性的三视角检查**——

| 视角 | 它问的问题 | 输入（全是现成读数） |
|---|---|---|
| 激进 | 凭什么不重仓？还有多少上行空间没算进去 | 目标位距离、板块动量、相对强度 |
| 保守 | 最坏情况亏多少？跳空、跌停、流动性够不够跑 | ATR、`screens/liquidity.py`、`regime` 档位 |
| 中性 | 折中仓位是多少 | 前两者的输出 |

三者输入全部来自确定性层，输出是一个**带三条对立理由的仓位区间**，而不是一个数。
这既拿到了「对抗」的价值，又不违反「数字只在确定性层产生」的规矩。

### 3.2 Reflection + 情境检索记忆（次值得借）

**它的做法**：一轮决策兑现后，按收益让 LLM 反思每个角色错在哪，把「情境 → 教训」
压成一句话存进 ChromaDB；下次遇到相似情境，用 embedding 检索出历史教训注入 prompt。

**为什么这个和本系统的纪律兼容**：`journal/stats.py` 明确拒绝按统计回写权重（样本
不足时调参数是调噪声，「系统会看起来在进步，实际在漂移」）。而情境检索**不改任何
权重**——它检索的是**先例**。

> 「上次也是退潮期 + 放量突破 + 顶背离，结果如何？」

这是台账里**已经有的数据**，只是现在只能看聚合表，看不到相似案例本身。而且分组
维度已经齐了——`stats.py` 里有 8 个 bucket 函数（`_regime_bucket`、`_pullback_bucket`、
`_rotation_bucket`、`_turnover_bucket`、`_index_bucket`、`_entry_basis_bucket`、
`_decider_bucket`、`_score_bucket`），它们的组合本身就是一个现成的情境键。补上按
这个键的检索，`journal/` 就从「统计表」变成「可查的判例库」，而这一步不需要任何模型。

**但它的实现有两处不能照抄**：

1. **ChromaDB + embedding 对本系统是过重的依赖。** 本系统的情境维度是**有限且
   离散的**——上面那 8 个 bucket 函数已经把情境切成了有限个格子。直接建结构化索引
   即可，不需要向量检索。语义相似度在这里解决的是一个本系统并不存在的问题。
2. **它用 LLM 生成「教训」。** 本系统更该存的是**原始结果 + 当时的读数**，让人看，
   而不是让模型总结出一句可能过拟合的话。`MIN_BUCKET = 20` 那条纪律在这里同样
   适用：3 个样本总结出的「教训」比没有教训更危险。

### 3.3 硬停护栏（工程细节，直接可抄的做法）

`graph/conditional_logic.py` 里每个分析节点都有与模型判断**无关**的硬停条件：

- `max_tool_calls`（3 次，基本面是 1 次），达到就强制结束，注释直接写「死循环修复」
- 报告长度 > 100 字符即认定完成，不再循环
- 辩论轮次 `max_count = 2 × max_debate_rounds`，风险讨论 `3 × max_risk_discuss_rounds`

**本系统当前不存在这个风险**——`agents/debate.py` 是单轮直线（多头 → 空头 → 裁判），
没有循环。这条记下来是为了**将来**：一旦 debate 改成多轮，或 `ask/` 那条问答链引入
工具循环，必须同时把硬停条件写进去，而不是依赖模型自己说「我分析完了」。

另一处：`dataflows/data_completeness_checker.py` 把「数据够不够」做成显式闸门。
✅ 本系统对应物是 `adapters/freshness.py` 与 `adapters/validate.py`，**且更严**
（跨源校验、量纲反推、浮点卫生）。这一项不需要借。

## 4. 不建议借的

- **五分析师全 LLM 化。** 它的技术面分析是 LLM 读指标文本产出报告。本系统把这件事
  放在确定性层（`daily_technical.py` / `volume_price.py` / `intraday.py` …），LLM
  只能引用不能产出数字，`agents/__init__.py` 写得很清楚——「越界的整段丢弃」，输出
  还要过 `factcheck.py:review_output` 闸门。**往它那边走是退步**，会让「量比
  3.2」这种读数重新变得不可追溯。
- **基本面 / 社媒情绪的权重。** 超短周期（隔夜到 3 日）里基本面的信息量接近零，
  社媒情绪的噪声远大于信号。它是**通用框架**所以要全覆盖，本系统是**超短专用**，
  照抄这个角色表等于给主链路加两个纯噪声输入。
- **多轮辩论。** 它的 N 轮辩论对单票深度分析成立（一天分析几只票）。本系统盘前要
  处理全市场候选，每天 3 次 LLM 调用是刻意的成本约束（`debate.py` docstring
  已写明）。轮次乘上候选数是不可行的。

---

## 5. 一句话总结

TradingAgents-CN 值得借的是**「风险要单独辩一层」**和**「台账要能按情境查先例」**
这两个结构性思路；不值得借的是它把数字生产交给 LLM 的做法。本系统在数据可信度
上的纪律比它严，在决策的对抗性上比它弱——补的应该正是后者，而且要用确定性的方式补。
