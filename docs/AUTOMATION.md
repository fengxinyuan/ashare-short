# 自动化架构

现在的系统是**命令驱动**：人敲 `sector-scan`、敲 `advise`。目标形态是**调度驱动**：
系统按时间表自己跑、自己推，人只在想问的时候插一句。

这是个反转，但不需要重写。现有 `jobs/*.py` 全是纯函数（给参数、返回结果、不碰全局
状态），所以加三层就能翻过来：**调度层**决定什么时候跑、**状态层**让前后两次运行知道
彼此的结论、**推送层**把结果送出去。

```text
                    ┌──────────────┐
                    │  scheduler   │  时间表 · 交易日历 · 幂等 · 失败隔离
                    └──────┬───────┘
          ┌────────────────┼────────────────┐
          ▼                ▼                ▼
     jobs/*.py        monitor/loop      journal/*
     （纯函数）        （盘中循环）      （台账与兑现）
          └────────┬───────┴────────┬───────┘
                   ▼                ▼
              state/            notify/
    自选股·候选池·告警状态·台账   控制台 · 文件 · 飞书
```

## 二、两类 agent，边界必须划清

「多 agent 分析」这个说法里藏着本系统最大的风险点。所以拆成两层，**两层之间的分界
就是数字的产生位置**。

### 2.1 采集/计算 agent —— 确定性算子，不是 LLM

统一接口，并行执行，各自独立失败：

```python
@dataclass(frozen=True)
class Finding:
    agent: str
    ok: bool
    data: dict
    notes: list[str]

class Agent(Protocol):
    name: str
    def run(self, ctx: AnalysisContext) -> Finding: ...
```

| agent | 职责 | 复用现有模块 |
|---|---|---|
| `NewsAgent` | 市场级舆情采集 → 跨源去重 → 12 小时半衰期折权 → 按板块归因 | `news/` |
| `SymbolNewsAgent` | 个股新闻 + 该票当日公告 → 逐票情绪读数（进 `ScoreInput.news`，封顶 ±6） | `news/` |
| `LlmNewsClassifier` | 大模型舆情归因：板块 · 方向 · 事件 · 传导机制。**只出标签不出数字**，失败退回词典 | `news/llm_classifier.py` |
| `LimitPoolAdapter` | 涨停池 / 炸板池 / 跌停池 → 炸板率与最高连板，进大盘情绪 | `adapters/limit_pool.py` |
| `SectorAgent` | 成分股日线聚合成板块动量 | `sectors/momentum.py` |
| `PriceAgent` | 日线结构：趋势、均线、支撑压力 | `signals/daily_technical.py` |
| `StructureAgent` | 威科夫阶段 | `signals/wyckoff.py` |
| `IntradayAgent` | 分时结构：VWAP、日内位置、量能 | `signals/intraday.py` |
| `CapitalAgent` | 龙虎榜净额归因 | `news/akshare_source.py` |
| `RiskAgent` | ST/退市/否决性公告 | `screens/` |

叫 agent 是因为它们**自治、可并行、可单独失败、输出同一种结构**——不是因为里面有模型。
系统里**所有数字都只在这一层产生**。

并行是实打实的收益：分钟线是每标的一次 HTTP、串行 1.0 秒/只，8 线程降到 0.19 秒/只
（20 只 3.8 秒，实测）。这是监控循环可行的前提。

### 2.2 研判 agent —— LLM 角色，只做论证

在确定性层算完之后运行，**输入只有 fact bundle**：

| 角色 | 职责 |
|---|---|
| `BullAgent` | 从 facts 里找支持做多的证据，逐条引用 |
| `BearAgent` | 从同一份 facts 里找反对的证据 |
| `JudgeAgent` | 对比两方，指出关键分歧点和它取决于哪个价位 |

三者全部过 `writer/llm.py:unverified_numbers` 数字闸门。**它们不产生任何新数字**，
只产生论证结构。

价值在于：单个总结器天然倾向于把反面证据埋进从句里。强制拆成对立两方，会把「量比
3.2 倍」这种既能读成放量突破、也能读成情绪透支的读数顶到台面上，让人自己判。

默认只在 `morning` 和 `postclose` 开启（每天 3 次 LLM 调用）。**监控告警不走 LLM**——
见 §六。

## 三、自选股与候选池是两个列表

| | 自选股 watchlist | 候选池 candidates |
|---|---|---|
| 谁维护 | 人 | `morning` 每天生成 |
| 生命周期 | 持久，永不自动删除 | 当日有效，次日覆盖 |
| 监控频率 | 2 分钟（1 分钟线） | 10 分钟（5 分钟线） |
| 告警级别 | 全部 | 只推 ACTION |

混成一个列表会让人分不清哪些是自己决定要盯的、哪些是机器今早刚塞进来的。这个区分
比它看起来重要。

状态目录（`ASHARE_DS_HOME` 覆盖，默认 `~/.ashare-ds/`）：

```text
watchlist.json            自选股（人维护）
candidates.json           候选池（每日生成）
daemon_state.json         当日各任务完成情况，用于幂等与重启恢复
alerts/2026-08-03.json    当日告警状态，用于去重
journal/2026-08.jsonl     预测台账，按月
news_cache/               舆情缓存（已有）
```

## 四、盘中监控：按状态**跃迁**告警

09:35–14:55 每 2 分钟一轮，一个 4 小时的交易日是 **≈145 轮**。按状态告警会直接刷屏，
所以只在**跃迁**时发。

每个标的每个交易日维护一份状态：

```python
{"vs_entry": "below|inside|above",
 "vs_vwap": "above|below",
 "scenario": "强势延续|均价震荡|转弱回落",
 "stop_broken": bool,
 "targets_hit": [0, 1]}
```

| 级别 | 触发 | 重发规则 |
|---|---|---|
| `ACTION` | 进入买入区间 / 跌破止损 / 触及目标 | 每日一次 |
| `WARN` | 跌破分时均价 / 情景转弱 / 量比 > 3 / 突发否决性公告 | 15 分钟冷却 |
| `INFO` | 站上分时均价 / 创当日新高 | 30 分钟冷却，且只对自选股 |

跌破止损**每日只发一次**：反复穿越止损位时连发五条，人只会把通知静音。

## 五、数据时效是整套自动化的总开关

这是自动化和危险的分界线。

人工跑 `advise` 时，看到「非当日数据」的横幅会自己判断。自动推送没有这个环节——
**一条基于昨天数据的实时告警，比没有告警糟糕得多**。

所以监控循环的第一步不是取数，是验时效：

```text
每轮开始 → 检查最新 bar 的时间戳
  ├── 在当前交易日且滞后 ≤ 5 分钟 → 正常告警
  ├── 滞后 5–15 分钟             → 告警照发，但每条附时间戳与滞后量
  └── 非当日 / 滞后 > 15 分钟 / 两轮不推进
        → 发**一条**「数据源停更，监控已挂起」，然后停止告警直到恢复
```

「停止告警」不是「停止运行」：循环继续跑、继续检测恢复，只是不再产出交易含义的信号。

每条推送都带数据 as-of 时间戳。没有例外。

## 六、越紧急的输出，越不经过 LLM

| 输出 | 写作方式 | 理由 |
|---|---|---|
| 盘中告警 | 纯模板 | 秒级时效，LLM 增加 2–5 秒延迟与一次失败可能 |
| 执行卡 | 纯模板 | 全是价位，没有需要组织的语言 |
| 盘前/盘后简报 | LLM + 数字闸门 + 多空辩论 | 信息量大，语言组织有价值 |
| 对话 | LLM + 数字闸门 | 本来就是对话 |

LLM 不在关键路径上——Qwen 挂了，整条链路照跑，只是简报变成模板体。

## 七、「持续学习」拆成四步，只做前三步

样本量不够时的在线学习就是过拟合。诚实的路径：

1. **记账**（现在做）——每条建议落台账：标的、日期、分数、买入区间、止损、目标、
   板块、理由、facts 快照哈希。哈希是为了让「当时到底看到了什么」可复现。
2. **兑现核对**（现在做）——T+1..T+5 拉实际日线算：有没有进入买入区间？先碰止损还是
   先碰目标？最大有利偏移 MFE / 最大不利偏移 MAE 各是多少？
3. **统计**（现在做）——按分数分桶、按板块、按趋势状态、按威科夫阶段分组报兑现率与
   MFE/MAE 分布。给人看，不自动改权重。
4. **标定**（样本够了再做）——`scoring/lightgbm_provider.py` 的位置早就留好了。触发
   条件是**台账里有 200+ 条已兑现记录**，不是「攒了两周」。

第 1、2 步是第 3、4 步的前提，无论最后走不走模型都不白做。而且它顺带回答了一个现在
根本答不上来的问题：**这套规则打分到底有没有用**。

不做的：拿几十个样本拟合出来的「看起来在学习」的东西。

## 八、飞书推送

`notify/feishu.py` 补全为真实实现：

- webhook 从 `FEISHU_WEBHOOK_URL` 读，可选签名 `FEISHU_SECRET`
  （`timestamp\n{secret}` 的 HMAC-SHA256 base64）
- 飞书应用层错误也返回 HTTP 200，必须检 body 里的 `code`
- 按**字节**切分（`split_utf8_text` 已有，中文 3 字节/字）
- 永不抛异常：推送失败只返回 `False` 并记 note，不能拖垮分析

告警走紧凑卡片，简报走完整 markdown。控制台与文件通道始终保留——飞书挂了，本地仍有
完整记录。

## 九、实测约束

| 约束 | 实测值 | 设计后果 |
|---|---|---|
| 分钟线串行吞吐 | 1.0 秒/标的 | 串行轮询 50 只要 50 秒，不可接受 |
| 分钟线 8 线程 | 0.19 秒/标的，20 只 3.8 秒 | 监控循环可行；线程池是必需项不是优化项 |
| 单次响应体量 | 恒定 1970 根 | 无法只取当日；每轮下载量固定，与标的数线性相关 |
| **批量快照（新浪）** | **5 只 171ms，200 引用 308ms，带五档** | 比逐只拉分钟线快一到两个量级，**尚未接入监控** |
| **涨停价（腾讯）** | **69ms，10%/20% 板均正确** | 可替掉 `strong_count` 的 9.5% 近似，**尚未接入** |
| 日线批量 | 59 只 / 0.4 秒 | 盘前全市场扫描 30–60 秒 |

**未验证**：盘中持续轮询是否触发新浪限流。上面的并发测试跑在非交易时段、总量 40 次
请求；一个交易日是 145 轮 × 50 只 ≈ 7000 次。设计里必须留退路：

- 失败标的指数退避，不重试到死
- 连续失败率超阈值 → 自动降频（2 分钟 → 5 分钟 → 10 分钟）并推一条通知
- 降到最低频仍失败 → 挂起监控，等付费档

周一实测 `intraday-check` 时一并测限流。

> 后续改进：`adapters/snapshot.py` 的批量快照让「一次请求拿全部标的的现价与五档」成为
> 可能，接入后监控的请求数会从 `轮数 × 标的数` 降到 `轮数`，限流风险基本消失。目前
> 监控仍走分钟线，因为 VWAP 与日内结构需要 bar 序列——正确的形态是两者合用：快照给
> 现价与盘口，分钟线给结构。

## 十、失败模式

| 失败 | 行为 |
|---|---|
| 单个数据源挂 | 该 agent 的 finding 标 `ok=False`，其余照跑，简报里写明哪个源挂了 |
| 分钟线停更 | 挂起告警（§五），循环继续检测恢复 |
| 新浪限流 | 指数退避 → 降频 → 挂起，每次降级推一条通知 |
| LLM 不可用 | 回退模板，标注原因 |
| 飞书推送失败 | 返回 False，控制台与文件通道不受影响 |
| 单个任务抛异常 | 捕获、记日志、推一条失败通知，守护进程继续 |
| 守护进程崩溃重启 | 读 `daemon_state.json`，当天已完成的任务不重跑 |
| 非交易日 | 整张表跳过，不产出任何推送 |

## 十一、人的入口没有被自动化取代

自动化解决「系统主动告诉我」，对话解决「我主动问系统」。后者升级为读同一份状态：

```text
ashare-ds chat
  /watch          看自选股当前状态
  /alerts         看今天已触发的告警
  /journal 600519.SH   看这只票历史建议的兑现情况
  /sectors        看今早的板块排序
```

`chat` 因此从「一次性算完再问」变成「问的是自动化链路正在维护的那份状态」。
