# 设计决策与被否决的方案

这份文档记录**为什么是现在这样**，以及**哪些看起来合理的方案被否决了、依据是什么**。
写在这里是为了防止后续再被同类方案带偏——被否决的方案通常还会以新的包装回来。

---

## 一、集合竞价拦截：这条路封死了，不是钱的问题

某版「终极实盘闭环」方案的第二层是「09:20–09:25 竞价秒级引擎」。其中两处是
**A 股交易规则层面的逻辑不成立**，不是参数调优问题。

### 1.1 09:20–09:25 不接受撤单，撤单率公式恒等于 0（致命）

错误写法：

```text
R_withdraw = (BidAmount_09:24:30 - BidAmount_09:24:58) / BidAmount_09:24:30
```

A 股集合竞价 **09:20–09:25 期间交易所不接受撤单**。该窗口内买盘挂单量不会因撤单
下降，这个比值恒约等于 0，或只反映价格档位漂移，**无法识别诱多**。

撤单率只能定义在 **09:15–09:19:59** 这个可撤单窗口，且需要数据源提供逐笔委托或
撤单记录——**任何档位、任何数据源都不提供**。

### 1.2 「09:25:02 推送卡片 → 1.5 秒点击下单」在时序上是事后动作（致命）

09:25 集合竞价已经撮合完毕、开盘价已定。09:25:02 才推送，此时下单**无法参与集合竞价**：
沪市 09:25–09:30 不接受申报，深市虽接受但订单只进缓冲区、开盘后才进连续竞价。

这条链路实际产出的是一张 **09:30 的开盘单**，却按「竞价成交」的盈亏比在算，
**会系统性高估收益**。要参与竞价，决策必须在 **09:24:58 之前**完成。

### 1.3 结论：删掉，而不是留着等数据

`engines/auction.py`（221 行）与相关状态机（`AUC_FOCUS` / `AVOID_NOFILL` /
`AVOID_FAKE_STRENGTH`）已一并删除。它实现的是一个**用不存在的数据、在来不及的时刻
做出的决策**。

即使接上 QMT 也补不上：QMT 给的是券商侧五档与逐笔成交，**不是交易所的竞价撮合量与
未匹配量**。那个数据交易所根本不发布。

> **留下的教训**：在没有 L2 之前，竞价相关字段一律置空并标 `data_stale`，
> **不要用日线数据凑数**——把全天成交额填进 `matched_amount`，会让日线数字轻松通过
> 为竞价设计的三千万门槛。

## 二、四个会静默出错的公式

这些不是「不够精确」，是**在最需要它们的时候方向反号**。

### 2.1 `R_unmatched = Unmatched / Matched` 无上界

Matched 很小时该值可以是几十、几百，`> 60%` 的阈值失去意义。

正确形式，值域锁死在 `[0, 1]`：

```text
R_imbalance = Unmatched / (Matched + Unmatched)
```

### 2.2 `R_tail = NetInflow_last30m / NetInflow_total` 在净流出时符号翻转

全天净流出（分母为负）时比值符号翻转——**尾盘也在流出的票会算出正的大比例，
尾盘拉升的票反而算出负值**。这个判据在下跌市（恰恰最需要它的时候）会系统性误判。

正确做法：加方向门槛，仅当 `NetInflow_total > 0` 时才判定；否则标记为未定义、
不参与打分。

### 2.3 `F_market_emotion` 在 N=50 处不连续

分段函数在 `N_down = 50` 处从 `1.0 - 35/50 = 0.3` 直接跳到 `0.1`。**跌停 50 家和
51 家的市场状态几乎相同，仓位上限却差 3 倍**；盘中跌停家数在 50 上下反复穿越时，
仓位指令会来回翻转。

正确做法：连续段保持线性平滑，熔断做成**带滞回的独立开关**（进入阈值 55、退出阈值 45），
不要让熔断以断点形式混在连续函数里。

**这条已经推广成全系统的原则**：阶跃函数在阈值两侧给出差很多的分，而阈值本身是
拍脑袋定的，读数在附近来回穿越时排序就会抖。现在大盘层与个股层都用斜坡
（`_ramp(value, onset, full)`）。

### 2.4 `强度 = 命中密度` 在小样本上方向反了

板块舆情用 `intensity`（命中密度）加权时，**样本越小平均密度越高**。实测出现过
基础化工靠 2 条快讯拿满 +12、计算机 22 条只拿 +2.0。

正确做法：文档数不足 8 条时按 `条数/8` 折权。密度是密度，证据量是证据量。

## 三、C++/Cython 极速引擎 + 盘后冷编译：过度工程

方案要求「30ms 内纯原生算术校验」并配套「15:30 冷编译 C++ 引擎」。

**瓶颈从来不在算术**：几百只标的的比值运算在 CPython 里是亚毫秒级。真正的延迟在
数据源——TickFlow 是 REST 快照（百毫秒级往返），券商 L2 推送也在几十毫秒。

为占比不到 1% 的环节引入 C++ 工具链和每日编译流程，换来的是运维负担和一条**无法热修
的关键路径**。

**保持纯 Python。**

## 四、威科夫：借概念，不借体系

这个项目借用威科夫的**结构概念**作为一层轻量覆盖，不是完整的自由裁量交易体系。

**保留**：吸筹/派发倾向、Spring 与 Upthrust 识别、SOS/LPS 确认、
effort vs result、压缩后扩张。

**丢弃**：重量级 agent 编排、策略膨胀、把不透明的 prompt 当主决策层。

**在本项目里**：

- `WyckoffAnalyzer` 把历史 bar 打成结构倾向
- `DailyTechnicalAnalyzer` 抽支撑、压力、趋势状态、形态提示
- 结果只用于研究，不下单

**转向低吸口径之后，威科夫的权重重排过一次**：

| 事件 | 原权重 | 现权重 | 理由 |
|---|---|---|---|
| MARKUP（主升段） | +12 | **+7** | 主升段是**追高**的位置 |
| ACCUMULATION（吸筹末端） | +10 | +10 | 低吸该待的地方 |
| Spring（假跌破收回） | +6 | **+8** | **就是低吸信号** |
| LPS（回踩承接） | +4 | **+7** | **就是低吸信号** |
| SOS（放量上推突破） | +5 | **+3** | 强势确认，对追涨有用，对低吸是「已经晚了」 |

**阶段本身只说明「趋势没坏」，真正的进场信号是事件。** 原来的排序把追高排在了回踩前面。

用法：当交叉验证，不当唯一真相来源。

## 五、「持续学习」不做成在线学习

样本量不够时的在线学习就是过拟合。

**不做的**：拿几十个样本拟合出来的、看起来在学习的东西。

**做的**：记账 → 对照组 → 兑现核对 → 统计，**只到这里为止**。上模型的触发条件是
台账里有 **200 条已兑现记录**（`journal/stats.py:MODEL_READY_SAMPLES`），
不是「攒了两周」。在那之前统计只报告、不回写任何权重。

### 为什么必须有对照组

没有负样本就永远回答不了「**筛选规则本身有没有用**」。入选组次日涨 1.2% 听起来不错，
但若对照组涨 1.4%，这套规则就是**负价值**。

对照组取**紧邻落选**而不是全市场垫底——后者差出来的是「好票 vs 烂票」，不是规则的价值。
等量是为了让两组的统计噪声量级可比。

### 为什么必须存当时的大盘状态

同一套规则在退潮期和启动期的期望值可以是**反号**的。不把炸板率、最高连板、涨跌停家数
和大盘读数存进每条记录，事后就无法按情绪周期分层。

**冗余存储是刻意的**：台账是 JSONL，每条多带七八个数比事后按日期 join 便宜得多，
而且**记录自带分层维度**意味着任何一段区间的数据都能独立分析，不依赖别的文件还在不在。

### 为什么两套持有期口径并存

`next_open/high/low/close` 对应「次日就卖」，五日 MFE/MAE 对应低吸的自然持有期。
**哪种更合适现在拍板都是猜，两个都记让数据回答。**

隔夜跳空单独记，是因为持仓过夜的收益里它常常比日内择时贡献更大，混在 MFE 里就归因不出来。

### 特征必须在采集之前定好

台账字段一旦漏了，之前的样本就**永久失去分层能力**——两个月后才有足够样本回答
「回撤 5% 买和回撤 8% 买哪个次日溢价高」，那时再想补字段已经晚了。

所以 `signals/dipbuy.py` 只负责**算出这些数**，不负责打分：打分口径还在观察期、随时会调，
特征定义不该跟着抖。

## 六、买卖点：为什么是「候选集 + 裁决」而不是两个极端

### 全部写死是错的

那些阈值——回调 5% 算深、量比 1.0 算放量、盈亏比 2.0 达标、买入区间 = VWAP ± 12%
日振幅——**没有一个是拟合出来的**。它们看起来精确，实际是一组从未被验证的猜测，
而且用一个数掩盖了「这里本来有多个合理答案」这个事实。

### 全交给模型也是错的

同一份数据两次调用会给出不同的价，而且回答不了「为什么是 22.95 不是 22.80」。
台账里记下来的东西因此无法归因，整个持续学习的链条断掉。

### 所以分界线画在「谁能产生数字」和「谁能做取舍」之间

- **规则产生所有数字，并给出一组带出处的候选**（含自己的默认排序）
- **模型只在候选集内做取舍**，必须引用 L1 读数说明理由，可以弃权，**不能造价**
- **数字闸门比通用闸门更严**：价格必须**恰好等于**某个候选，不接受近似匹配
  ——22.95 和 22.96 在文本比对里都能过，但那是两个不同的挂单价
- **LLM 挂了就取默认排序**，链路照跑

### 这个决定本身也要被验证

台账**同时记录规则默认与模型裁决两套结论**，兑现核对对两套各算一遍。
「加了裁量权有没有用」因此是一个**有数据能回答**的问题。

在样本够之前，这条记录在文档里：**给模型裁量权是因为写死的阈值同样没有依据，
不是因为有证据说模型更好。**

## 六b、为什么是「周期闸门 + 打法分支」而不是继续调权重

上一轮把打分口径从追涨转成低吸，改的是**权重的符号**（MARKUP 12→7、缩量从 −5
改成正分、阶跃换斜坡）。2026-08-03 的实盘输出说明那一轮没修完：

```
60 条建议  →  54 条只是 shallow 回调、52 条是**放量**回调、0 条下跌趋势
当日炸板率 51.94%（系统自己的定义里 ≥50% 即退潮），仓位系数照给 0.68
```

### 继续调权重解决不了

缩量在打分里占 ±6 分，而 trend + wyckoff 占 50。把缩量加到 ±20 也压不过
「趋势强 + 威科夫结构好」的组合——**只要它是权重，就可以被别的项买回来**。
这和 §六「全部写死是错的」不是同一件事：那里说的是阈值该不该由模型取舍，
这里说的是**某些条件根本不该参与加权**。

「回调放量」不是一个减分项，它是「这不是回踩」的定义。定义必须是门槛。

### 同一条教训第二次被应用：业绩不进打分

2026-08-04 接入业绩预告层（`adapters/earnings.py`）时，这条结论被**原样复用**，
并且真的挡住了一次重犯：

开发过程中一度出现 `_score_earnings` 给 `is_strong_catalyst` 加 **±6 分**——
和上面那个缩量的数字**一模一样**。它看起来很有道理（中报预增 +1197% 的票凭什么
和普通票同分），但没有任何回测支持这个幅度，而它一旦是权重，就会在
「趋势强 + 威科夫好」的组合面前被买回来，同时又足以在别处把一只本不该入选的票
顶进候选。

**最终口径是双面不对称的：**

| | 处置 | 为什么 |
|---|---|---|
| 亏损 / 大幅预减 | **门槛**，打分前移除标的 | 「中报窗口内在亏钱」是一个定义，不是一个程度 |
| 预增 / 扭亏 | **只进理由、台账、简报措辞，不产生分数** | 未经回测的正向读数一律先落台账 |

`_score_earnings` 因此返回 `None` 而不是 `0.0`，`EARNINGS_CAP` 常量被删除而不是
设成零——一个存在的上限常量迟早会有人把它接回 `total`，而返回 `None` 的函数
没法被 `total +=` 用上，改回去必须是一次**显式的、看得见的**改动。

### 否决必须留下可核对的痕迹

业绩门槛是这套系统里唯一一道**明知有代价还是加了**的闸门：它会挡掉亏损但正当红
的题材股，而那在超短线上完全可能是当期最强的品种。

所以它必须自带账单。台账新增 `KIND_VETOED` 一类，被否的标的按同一套兑现流程核对
（参考价从板块动量已取的日线里拿，零额外请求），`journal/stats.py:_veto_cost`
算「否决组 − 入选组」。**正数意味着这道闸门在帮倒忙。**

这和对照组（`KIND_CONTROL`）问的不是同一件事：对照组问「排序有没有用」，
否决组问「这道闸门拦对了没有」。后者此前根本无法回答——被否的标的在打分之前就
消失了，台账里连名字都没有，于是代价只能停留在设计者的自述里。

范围限定在**被选中板块内**的否决对象：全市场 284 家首亏与这次筛选无关，记进来
会让两组不再同源，差值就不再是这道闸门的代价。

### 同一份裁决在两条链路上强度不同

`morning` 否决，`advise` 只置顶警告。这不是不一致，是**「谁在提问」不同**：
前者是系统主动从几千只里选，后者是你点名问一只票——「这只票我不给你看」是最没用
的回答。ST 筛选已移除；这条不对称口径现在只适用于业绩否决。

### 被否决的两个替代方案

**只加一个「今天别做」的开关。** 最省事，但它只解决炸板率那一个问题，回答不了
「上涨趋势什么样的可以买」。而后者是这套系统从来没有能力表达的东西——趋势一直
是权重，权重表达不了「不同趋势走不同判据链」。

**直接上机器学习/因子模型。** 现在台账只有 2 个交易日、0 条已兑现。没有回测
基线的情况下，ML 只会更快地过拟合到这两天。**顺序必须是先有分支、再有回测、
最后才是模型**——反过来做，模型学到的是当前这套有缺陷门槛的输出分布。

### 为什么闸门的切点和台账分层共用一组常量

`journal/stats.py` 现在从 `strategy/regime.py` import 切点。两边各定一套是个
隐蔽的坑：闸门按 0.50 切、统计按 0.55 切，那么「退潮期这套规则管不管用」的样本
就和**真正被闸门拦下的那些日子**对不上，闸门永远无法被自己的台账验证。

改造前恰好就是这个状态——`stats.py` 用 0.30/0.50，`sectors/predict.py` 用
0.25/0.55。后者是连续斜坡（另一种数学对象）所以保持独立，前两者已统一。

### 情绪周期的判定存标签，不是只存原始读数

台账 `market_state.regime` 存的是**当时闸门实际判定的那个标签**，统计分组优先
读它、只有老记录才回退到用炸板率现算。理由同上：分组必须和当时生效的判断一致，
否则改一次阈值就会让历史样本重新分组，而那些样本对应的是旧阈值下的行为。

## 七、其余已固化的决定

| 决定 | 理由 |
|---|---|
| **筛选与打分分离** | ST、退市、立案调查这类风险无法被好走势补偿，做成扣分迟早被其他因子的正分盖过 |
| **没数据 ≠ 中性** | 给中性默认分会让「无知」压过「测量出的走弱」 |
| **数据缺失时放行而非拦截** | 用「没测到」当否决理由，等于让数据缺失冒充风险判断 |
| **越紧急的输出越不经过 LLM** | 盘中告警秒级时效，LLM 增加 2–5 秒延迟与一次失败可能 |
| **合规文本程序化追加** | 实测 Qwen 在被明确要求保留时，仍会在概括中整段丢掉风险提示 |
| **按跃迁告警而非按状态** | 145 轮/天，按状态告警到中午就被静音了 |
| **止损每日只发一次** | 反复穿越止损位时连发五条，人只会把通知静音 |
| **止损与目标开盘 15 分钟后钉死** | 每轮重算的止损永远在当前最低价下方，`stop_break` 结构上无法触发——跟着价格往下走的止损不是止损 |
| **自选股/候选池/热门股三个列表分开**（热门股 ⬜ 未建） | 混在一起就分不清哪些是自己决定要盯的、哪些是机器刚塞进来的 |
| **热门股不进台账**（⬜ 未建） | 入选条件随盘中情绪变，混进去会污染「盘前筛选有没有用」的样本 |
| **同花顺行业指数不参与打分** | 90 个行业 ≈ 申万二级粒度，硬映到一级只会造出假精度 |
| **五档只做有界旁证** | 挂单可撤可假挂且只有五档；当主判据等于把仓位押在别人随时能撤的单上 |
| **裁决器输出 key 而不是价格** | 提示词说「不许编」是请求不是约束；只给「指一个已有的数」的通道才是约束 |
| **弃权是一等公民** | 规则层永远能算出价位，表达不了「今天不该买」——那是裁决层最有价值的增量 |
| **裁决器不进盘中循环** | 每标的一次 LLM 调用，20 只票 = 20 次往返、二十个失败机会，而告警要秒级 |
| **规则默认无条件进候选集** | 否则闸门会把引擎自己报的价判成越界，且台账两个字段静默对不上 |
| **挂单墙门槛按当日成交额缩放** | 固定金额在 3 元的票和 1350 元的票上无法同时成立 |
| **委比在涨跌停上单独标退化** | 恒等于 ±1.0，混进排序会让买不进的涨停票永远排第一 |
| **分片取数失败就抛错且不写缓存** | 宁可跑不出来，也不留一份不知道完不完整的分类 |
| **语料库用 SQLite，其余用 JSON/JSONL** | 它是唯一需要按板块/标的/时间窗**查询**且长期累积的数据 |
| **不产出概率/胜率/预期收益率** | 没有拟合模型能支撑它们 |

## 九、这一轮建三层时发现的两个静默缺陷

两个都属于「不会报错，只会悄悄变成另一件事」，都不是这次改动引入的。

### `/debate` 每一次调用都抛 TypeError

`chat/session.py` 里写的是 `session.has_facts()`，而 `has_facts` 是 property。
调用它等于去调用一个 `bool`。上下文空不空都一样炸——空的时候 `not False` 先求值，
`False()` 照样抛。

它活下来的原因值得记：**辩论层本身测过四条，但从对话入口进去的那条路一条都没有。**
测了「零件能转」不等于测了「装上去能转」。修复只有一个括号，补的测试才是重点。

### 五档快照的量纲取决于是哪个源答的

`Snapshot` 一个 `volume` 字段，新浪填股、腾讯填手。此前没有消费者同时用两个源，
所以没炸；这次要把五档接进买卖点，两边的挂单量要放在一起比，差 100 倍会让挂单墙
判定完全失效——而且不会报错，只会给出一个错误的价位。

同一个数据类承载两个源时，**量纲契约必须在解析层就统一**，不能留给下游。

### 顺带关掉的一类测试泄漏

`OrderBookAgent` 在没拿到 adapter 时会自己构造一个真的 `SnapshotAdapter`——生产
里这是对的，测试里这是一次静默外网请求。实测每个 `run_advise` 测试都在打
`qt.gtimg.cn`，只是网络快，看起来像没打。

和 `conftest.py` 里那条凭据泄漏同源：断网的机器上它变成几秒超时，网络好的机器上
它让测试依赖一个第三方站点的可用性，而没有任何一条断言是关于那个站点的。现在
默认源在测试里被钉成 `None`，要测五档的测试自己注入。

## 十、这一轮全仓清理：把复制出来的东西收成一份

清理的判据只有一条：**同一件事在几个地方各写了一份，而每一份都略有不同**。
重复本身不贵，贵的是每一份漏掉的那一项都不一样，于是缺陷只在其中几条路径上出现。

### `numeric.py`——九份 `_float` 收成一份

仓库里有九个数字收口函数（`_float` / `_number` / `_num`），没有两份的判据是一样的：

| 变体 | 挡空串 | 挡 `"-"` / `"null"` | 挡 NaN | 挡 ±inf | 挡 `bool` |
|---|---|---|---|---|---|
| `limit_pool` / `sina_intraday` | ✗ | ✗ | ✓ | ✗ | ✗ |
| `market_scan` / `tickflow_market` | ✓ | ✓ | ✗ | ✗ | ✗ |
| `validate` | ✗ | ✗ | ✓ | ✓ | ✓ |
| `dipbuy` | ✓ | ✗ | ✓ | ✗ | ✗ |
| `snapshot` | ✗ | ✗ | ✗ | ✗ | ✗ |

**没挡 NaN 的那几份是真的风险**：NaN 不会抛异常，它会一路参与比较，而 NaN 的比较
恒为 False——「跌破止损」于是静默变成「没跌破」。现在统一成一条判据：能变成有限
实数就要，否则一律 `None`，下游只判 `is None`。

`snapshot` 那一份额外把 `0.0` 当缺失（停牌时行情源回 `0.00`），保留为
`positive()`；它同时也挡掉了负价，比原来的「非零即可」更严。

另有五份「按几个字段名依次试」的变体收成 `first_finite()`。

### 另外三处逐字重复

| 收到哪 | 原来散在 |
|---|---|
| `schedule/clock.py::minutes_since_open` | 三个适配器各一份。算的是**市场规则**（午休那 90 分钟要挖掉，否则量比系统性偏低四成），不是某个源的解析细节 |
| `advice/view.py` | `ask/context.py`、`chat/session.py`、`monitor/triggers.py` 各写了一份排序键、换手率/成交额拼接、买入区间格式化。漂移的后果是同一只票在 `ask` 里排第一、在 `chat` 里排第四，而两边读的是同一个 JSON |
| `notify/base.py::publish`、`adapters/snapshot.py::default_snapshot_adapter` | `monitor/loop.py` ↔ `schedule/daemon.py`、`agents/collectors.py` ↔ `jobs/monitor.py` |

### 再一轮扫出来的四处

| 收到哪 | 原来散在 | 重复之外的代价 |
|---|---|---|
| `adapters/base.py::security_names` | `jobs/morning.py`、`jobs/post_close.py`、`monitor/session.py` | 无。纯展示字段，三份行为一致 |

### `cli.py`：一条 if 链和一段两百行的顺序代码

两处都不是「逻辑复杂」，是「一个函数里塞了十六份互不相干的东西」——
`PLR0915` 数出来的 139 条语句里没有一个分支。

| 原来 | 改成 | 为什么值得动 |
|---|---|---|
| `main()` 里 16 段 `if args.command == "X": ... return` | `COMMANDS` 表 + 每条命令一个 `_cmd_*(args)` | 分支之间没有任何共享逻辑，它们只是碰巧写在同一个函数里。拆开之后每条命令能单独调用和测试，`main` 只剩「取参数、查表、执行」三行 |
| `build_parser()` 220 行顺序 `add_argument` | 每条命令一个 `_parser_*(subparsers)` | 加一条命令 = 加一个函数 + 加一行，而不是往两百行里再插十行 |

`main()` 原来的 16 个 `return` 现在由字典查表替代。**没有加 fallback**：
`subparsers` 是 `required=True` 的，命令名一定在表里；真取不到就让 `KeyError`
抛出来——那种情况是接线漏了一条命令，不该悄悄什么都不做。

改动本身零风险，但验证方式值得记：把 `build_parser()` 的**全部** subcommand、
flag、default、choices、help 序列化成 JSON，改前改后 `diff` 为空。argparse 的
接线错误（少一个 flag、default 变了）不会让测试红，只会让某个开关某天不生效。

### `tabular.py`——`numeric.py` 的另一半

`numeric.py` 管**单元格里的数**，这个模块管**表的形状和单元格里的字**。同一件
事的两半：akshare 这类源有时给 `DataFrame`、有时给 `list[dict]`、拿不到时给
`None`，每个适配器都得先把三种情况抹平才能开始干活。

六个文件各写过一份，其中**三份逐字相同**（`earnings._records`、
`sina_intraday._rows`、`akshare_source._rows`），已收进 `records()`。

真正值得记的是 `text()` 挡掉的那三个字符串：

```python
"nan"  "none"  "nat"     # pandas 把缺失值 str() 之后的样子
```

**它们会通过所有非空判断。** `bool("nan")` 是 True，`title or "无标题"` 拿到的
是 `"nan"`。一条没有标题的公告，标题字段会变成字符串 `"nan"` 并一路印进简报——
不报错，只是简报里多一行 `nan`。和 `numeric.py` 挡 NaN 是同一类问题：**必须在
解析层变成缺失值，因为下游判的是 `is None`，而这三个都不是 None。**

`akshare_adapter` 与 `tickflow_adapter` 那两份没有并进来：前者把非 dict 元素
包成 `{"value": item}`，后者要处理紧凑 K 线载荷，语义确实不同。
`chip_distribution` 那份自带 `try`（「取不到就当没有筹码数据」），也留着。

### `PLR0911` 的阈值：把 6 提到 10，而不是去改代码

`ruff` 默认允许一个函数有 6 个 `return`。全仓 1168 个函数里超过 6 的只有
**1.5%**，逐个看过之后**没有一个是「一个函数干了两件事」**，全部是两种形状：

| 形状 | 例子 | 为什么 return 多是对的 |
|---|---|---|
| 分档判定阶梯 | `wyckoff._classify_bias` | 评分映射到 7 个结构档位，**顺序本身是语义**（前面的规则覆盖后面的）。改成查表就丢掉了覆盖关系 |
| 类型分发 | `qmt_xtdata._to_plain` | 要认 numpy 交出来的 8 种形状，有几种形状就有几个 `return` |

两种都是卫语句风格，摊平比嵌套好读。**这条规则在这里罚的是正确的写法**，所以
调阈值而不是改代码——`max-returns = 10`。10 不是照着现状凑的数，是「一次分发
或一条阶梯」的天花板：再多基本意味着在两个维度上同时分发，那才是该拆的信号。

分支数与语句数超标的那几个走 `per-file-ignores`，并且和早先那四个**分开列**：
前四个是「以后要拆」，后加的六个是**已经看过并决定不拆**（`monitor/loop.py` 的
5 份循环状态、`daily_technical.py` 的 SVG 坐标计算、适配器的字段兜底、审计脚本
的线性过程）。两类欠账混在一张名单里，过两个月就分不清哪些还欠着。

至此 `ruff check .` 全仓退出码为 0，这道闸门可以进 CI 了。

### 顺带修掉的一个闭包

`jobs/morning.py::_record_journal` 在 `for item in candidates` 里定义 `pct()`，
闭包捕获的是**循环变量** `reference`。今天没出事，只因为它每轮都立刻调用；

参考价——**不报错，只让台账里的百分比整体偏掉**。提为模块级
`_pct_against(value, reference)`，参考价变成显式入参。

### 顺带修掉的一个 NameError

`chat/session.py` 的 `_render_generic_summary` 调用了一个**在该模块里不存在**的
`_short()`——函数是从 `ask/context.py` 抄过来的，抄漏了它依赖的那个助手。

### 留下来没动的一处：`wyckoff.py` 的 EXHAUSTION 打分

```python
score -= 8.0 if close_position >= 0.5 else 8.0
```

两个分支都是 `8.0`，所以 `close_position` 这个判据是**死的**。邻近的 ABSORPTION
写的是 `+8.0 if ... else -8.0`，对称地看原意应该是
`-8.0 if close_position >= 0.5 else +8.0`。

**没有改。** 改它会直接改动评分输出，那是口径决策不是清理；而且没有任何一条测试
覆盖这个分支，改完也没有东西能告诉你改对了。已在代码里标注。

（`DTZ` 这一条后来收窄了，只剩两个子规则被忽略，见 §11.3。）

这种信噪比下没人会看第二次。现在显式列出规则族并逐条写明为什么忽略，
`ruff check` 的产出降到个位数，是一道能用的闸门而不是一堵墙。

## 十一、2026-08-09 这一轮：口径没收敛的四处

和 §十 不同——那一轮收的是**逐字重复的代码**。这一轮收的是**同一条约定被写下来
之后只执行了一半**，四处的失效方式一模一样：文档里承诺「只有一个来源」，代码里
有两到十个来源，而每个来源都对，直到某天不对。

### 11.1 词表：`news/lexicon.py` 说「加一个词是一行改动」，但有四份

`lexicon.py` 的模块注释写着改一个词只需改一处。实际上 `news/events.py` 与
`scoring/context.py` 各有一份自己的 `RISK_TERMS` / `EVENT_TERMS` / 供给词表。
代价不是重复本身，是**两层看同一条新闻会得出不同结论**：简报层认得「退市风险
警示」，打分层不认，于是那条风险出现在简报里、没有进评分。

顺带修掉一个真错：风险分原来按**命中词数**扣分，而「退市风险警示」同时命中
`退市` 和 `风险警示`，一条公告被罚两次。改成按**类别**计数。

### 11.2 线程池：`fanout.py` 说「必须收口」，但仓库里还有十个

`fanout.gather` 的模块注释把理由写得很清楚——保序与失败语义不一致时，同一条
链路在不同源上的行为会不一样，而这种不一致**在盘前是查不出来的**，它只表现为
「今天这一路没进来」。写完之后，十处手写 `ThreadPoolExecutor` 一处都没改。

现在全部收口，`ThreadPoolExecutor` 只允许出现在 `fanout.py`（有测试钉住）。
唯一保留自己吞异常的是 `agents/base.py`：agent 的失败不是「少一路」，是一份带
耗时和错误类名的 `Finding`，而耗时只有在闭包内部才量得到——**这是设计，代码里
写明了**。

顺带分开了舆情归因的两条失败路径：「调用没打通」与「模型答了但答的没法用」原来
共用一句「N 批失败」。前者查网络与配额，后者查提示词与 `max_tokens`。

### 11.3 时钟：`schedule/timezone.py` 说「避免依赖部署机器的系统时区」

然后 25 个文件里有 58 处 `datetime.now()` / `date.today()` / `fromtimestamp()`，
每一处都按**宿主机时区**展开。开发机装的是 `Asia/Shanghai`，所以一直是对的。

**在 UTC 容器里差 8 小时，而且两种错法都不报错：**

| 症状 | 后果 |
|---|---|
| `date.today()` 在北京 08:00 之前返回前一天 | 盘前跑批就在 08:30，整轮按昨天的交易日算 |
| 时效折减拿 `published_at`（北京裸串）减 `datetime.now()` | 当天的快讯整批被判成超龄丢弃 |

**注意问题不是「没带 tzinfo」。** naive 是有意的决定（全系统只有一个交易时钟，
带上 tzinfo 只会让 09:15 / 15:00 这类边界判断多一层转换），这条不改。要改的是
naive 的**北京**时间和 naive 的**宿主机**时间被当成了同一回事。

闸门从 ruff 来，不是手写守卫：`DTZ` 从整族忽略收窄到只留 `DTZ007`（strptime 吃
数据源给的北京裸串）与 `DTZ901`（`datetime.min` 当排序哨兵），取当前时刻的七条
全部放开。收口后在 `TZ=UTC` 下跑全量，抓出两条测试自己的宿主机时区依赖——它们
用 `datetime(...).timestamp()` 造 epoch，那是按宿主机时区解释的。

### 11.4 数字闸门：一个常量两份定义，一道闸门两个来源

`ORDINAL_CEILING = 20`（多小的整数算「第 3 档」这类序号，不必追溯）在
`writer/llm.py` 与 `advice/adjudicate.py` 各定义一份，而 `advice/external.py`
从**两个不同模块**分别拿这道闸门的两个常量。两份 20 漂成 20 和 15 不会让任何
测试变红，只会让同一个「第 18 档」在简报里放行、在裁决里作废。

收进包根的 `factcheck.py`（理由同 `numeric.py` / `fanout.py`：它约束的是一件
横跨三层的事）。**三道闸门严格程度不同是有意的，没有统一**：

| 闸门 | 严到什么程度 | 为什么 |
|---|---|---|
| `unverified_numbers` | 允许按写出的精度四舍五入，认 万/亿/% 后缀 | 散文改写本来就在重排数字 |
| `offending_numbers` | 只认数值相等 | 22.9512 写成 22.95 是另一个挂单价 |
| `_untraceable_numbers` | 只认 token 原样出现 | 外部裁决包不做量级换算 |

共用的只是「数字长什么样」和「哪些小整数是序号」。

### 这一轮的验证方式

每条收口都配了一个**结构守卫**（AST 扫 `src/`，或直接交给 ruff），而不是只补
行为用例：行为用例只有在有人恰好想到那个词、那个源、那个时刻的时候才会发现漂移。
守卫全部做过变异验证——把违规写法塞回去，确认它真的变红。

## 十二、竞价/开盘读数：把 §一 的删除做完

§一 删掉了竞价**决策层**（`engines/auction.py` 与三个状态机），理由是那套逻辑
「用不存在的数据、在来不及的时刻做决策」。ROADMAP §589 把结论固化成一句「不做
集合竞价拦截」。

**但采集层没删。** 到 2026-08-09 为止仍然完整存在：

```text
adapters/base.py        get_auction_features / get_open_features  两个 @abstractmethod
akshare / qmt / tickflow  六份实现
adapters/mapping.py     整个模块——券商字段别名归一层，两个 public 方法都只服务上面那六份
models/schemas.py       AuctionFeatures / OpenFeatures
cli.py                  --profile-file 开关 + QmtXtDataAdapter(profile=...)
examples/               custom_mapping_profile.json
```

`src/` 里**没有任何消费者**。`AuctionFeatures` 的 docstring 甚至自己写明了这一点，
并给出保留理由：「留着是因为归一层（`adapters/mapping.py`）已经在用它当券商字段的
落点」——而归一层存在的唯一目的就是产出 `AuctionFeatures`。两个模块互相引用对方
作为自己存在的理由，谁都不被第三方使用。

### 为什么是删而不是留

留着的成本不是那几百行。是这一层**看起来是活的**：它有抽象方法（所以每个新适配器
都必须实现它）、有归一契约、有测试、有 CLI 开关。任何人读到这里都会得出「这套系统
能取竞价数据」的结论，而 §一 的结论恰恰是这个数据**交易所根本不发布**。

`docs/INVENTORY.md` 存在的理由就是消灭这种假象，而它的三条口径全都漏掉了这一层：
模块级说 `adapters/mapping` 是活的（`cli.py` 确实 import 了它），符号级说
`get_auction_features` 是活的（它是抽象方法的实现），字段级只看 dataclass。
**盲区是「被接线的类上、没有调用方的公开方法」**——这一轮是靠单独扫一遍
public 方法的引用点发现的，扫出 13 个，竞价这一层占了 6 个。

### 删掉之后

净减 **约 950 行**（src + 测试），`MarketDataAdapter` 的契约从 6 个抽象方法降到 4 个。
连锁清掉了 14 个随之失去调用方的私有辅助（`_build_auction_payload` 101 行、
`_build_open_payload` 59 行、`_volume_multiplier` 23 行……），这些是 ruff 的
`F401` 看不见的那一类死码——**私有方法没有「未使用」告警**。

顺带露出一处旧账：`schedule/clock.py` 是 §十 为了收掉三个适配器里逐字重复的
`minutes_since_open` 才建的，而那三处调用点全在 `get_open_features` 里，删完之后
它一个调用方都不剩了。与此同时 `signals/intraday.py` 里一直有**第四份**私有实现，
被调用 6 次——当初的收口漏了它。现在收成一份，差别（钳顶到 240）留在调用方并写明
理由：`clock` 那份答「现在几点了」，收盘后必须继续走；`intraday` 那份答「这根 bar
落在第几分钟」，那个量按定义不超过 240。全天 86400 秒逐秒比对，新旧实现零差异。

## 十三、方法级盲区扫出来的其余几处

§十二 用「被接线的类上、没有调用方的公开方法」这条扫法找到了竞价那一层。同一次
扫描还剩 13 个，逐个看下来分成三类。

### 13.1 `dump_snapshot` × 3：同一条判据只执行了一半

§八 的删除表里已经有一行「`dump_snapshot_to_file`（× 3 个适配器）｜ 调试期的落盘
助手，零调用方」。**而 `dump_snapshot` 本身活了下来**——同样零调用方、同样连测试
都没有，83 行。它唯一被提到的用途写在 `qmt_xtdata.py` 的报错文案里：「Run
`qmt-dump` and update the mapping profile if needed」，而 `qmt-dump` 这条命令不
存在，mapping profile 在 §十二 已经删了。连锁清掉 7 个随之失去调用方的私有辅助，
共 **150 行**。

### 13.2 `TradingCalendar.refresh_from`：不是死码，是**没有入口的活代码**

这一个和上面几处性质不同，它是一处**运行中的缺口**：

- `holidays.json` 是节假日判定的第二层（第一层是周末，第三层是数据源实证）；
- `refresh_from` 是全仓**唯一**能写这张表的代码，38 行，有 7 处测试引用；
- **没有任何命令或任务调它**，于是这张表在实机上是空的（0 假日 / 0 调休）。

后果是判定退化成「周末以外都算交易日」——2026-10-01 读作交易日。这**不是静默
错误**：`explain()` 会老实说「未配置节假日表，未经假期校验」，`is_trading_day`
也刻意偏向「跑」（模块 docstring 写明了这个不对称：假日误判成交易日只是白跑一轮，
交易日误判成假日是一整天没有监控）。但那张表除了手工编辑之外**没有任何补上的
办法**，而能补的代码就摆在那里。

补了一条 `ashare-ds calendar-refresh`。实跑：2026 年 242 个交易日、19 个假日，
国庆与春节从此判得对。**给不出日历时保持原状而不是清空**——半张表比没有表更危险，
它会让 `configured` 为真、`explain()` 不再提示「未经假期校验」，一张空表冒充成
校验过的。这条分支单独有用例。

### 13.3 剩下的：查询访问器与两处未接线能力

| 方法 | 判定 |
|---|---|
| `SecurityMaster.name_of` / `by_concept` / `by_industry` / `concepts_of` | 数据持有者上的小查询器（共 23 行），不构成「系统有这项能力」的假象，留着 |

| `NewsStore.sector_heat`（53 行）、`DailyKChartRenderer.render_svg`（97 行 + `_empty_svg`） | **建成·未接线**，且都是完整功能而非脚手架。接不接是产品决定，不是清理——单独列出来等一次判断，别默默留着 |

### 这条口径要能一行命令跑出来

方法级这条检查原来是临时脚本跑的，没有进 `scripts/inventory_audit.py`。**在它落地
成第四条检查之前，这一节的结论会和前三条一样慢慢过期**（§4 那句「一条不能一行
命令跑出来的口径，等于没有这条口径」说的就是这件事）。

**2026-08-10 落地了**，见 §十四。落地当天它就自己证明了这句话：同一条口径重跑一遍，
上面这张表**漏掉了 5 处**——临时脚本那次扫的是「有没有引用」，而它按全文 token 数，
把 `x.best`、`x.name_of` 这类**撞名**算成了引用。

## 十四、第四条检查落地，以及它当场找到的那根断线

§十三 结尾欠的那条口径补上了：`scripts/inventory_audit.py` 现在有 `check_methods`，
判据是**类上的公开方法在 `src/` 里有没有调用点**，引用只认 AST 的属性读取
（`obj.foo`）与字符串字面量（`getattr` 与按名字分发的表），不再用全文 token 数。

分两档，因为「没人调」有两种，代价不同：

| 档 | 判据 | 进不进退出码 |
|---|---|---|
| **零引用** | 定义之外全仓一个引用点都没有 | **进**。和模块、符号一样是二值事实 |
| **仅测试在调** | `src/` 里没有调用点，只有 `tests/` 在调 | 不进。测试证明它**能用**，不证明**系统在用**——这一档就是 INVENTORY §1「建成·未接线」的自动版，接不接是产品决定 |

第二档必须把测试单独摘出来数，不能沿用 `check_symbols` 那条「测试也是调用方」的
口径：竞价那一层（§十二）当年正是**有测试、全绿、零生产调用方**。

### 14.1 零引用那一档：6 处，已清空

`QmtXtDataAdapter.get_full_tick_raw` / `get_l2_quote_raw`（18 行，连带私有的
`_call_optional`）与 §13.1 删掉的 `dump_snapshot` 同族——都是 mapping profile 时代
的裸透传，那个时代在 §十二 已经结束了。`StockAdvice.has_playbook`、
`BroadIndexRead.best`、`EarningsSnapshot.by_direction`、`SectorTaxonomy.sector_of`
是另外四处，其中两处值得单说：

- **`has_playbook`**（「今天有没有一条成立的打法」）零调用方，而
  `notify/render.py` 把同一个 `setup.get("matched")` **内联了一遍**。不是没人要
  这个判断，是要它的人没走这个门。
- **`SectorTaxonomy.sector_of`** 更贵：它和 `jobs/morning.py` 里的字典生成式是
  同一件事的两份实现，而**两份的并列规则是反的**（`setdefault` 留第一个 vs 生成式
  留最后一个）。活着的是没写下理由的那一份，跑的正好是反的。现在收成
  `sectors/base.py:reverse_index` 一份。

§13.3 判「留着」的 `EarningsSnapshot.by_direction` 这次改判删除：它连测试都没有，
而闸门一旦对它长期报警，报警本身就会先失效——那正是这份脚本要避免的结局。

### 14.2 仅测试在调那一档：`Recommendation.from_advice`

这一处不是死码，是**没有入口的活代码**，形状与 §13.2 的 `refresh_from` 相同，
但后果更隐蔽：

- `Recommendation.adjudication` 字段、把裁决压成可统计字段的 `_adjudication_record`
  （30 行）、读它的 `journal/stats.py:_adjudication_edge`（40 行）——**全都写好了**；
- 唯一的写入方是 `Recommendation.from_advice`，而它只有测试在调：`jobs/advise.py`
  从头到尾**没引用过 `journal`**；
- `morning` 那条链路不经过裁决层（盘前没有分时），所以它写的记录里这个字段恒为空。

于是「模型裁决比规则默认准不准」——`journal/records.py` 自己写着这是**加这一层时
唯一没法在设计阶段回答的问题**——在台账里永远是 `available: False`。它诚实地降级
（不是给一个错的数），但那个问题永远答不了。

**已接上**：`run_advise` 收一个可选的 `journal`，`jobs/advise.py:_record_journal`
把这一轮的裁决落台账。三条边界都写进了代码注释与用例：

1. **只有 `advise` 这条命令和守护进程 09:15 那一轮记。** `ask` / `facts` / `chat`
   也调 `run_advise`，但它们是**查**，不是发建议——把随口问到的标的记成「系统当天
   的建议」，事后统计就分不清哪些是系统主动给的。所以是依赖注入而不是默认打开。
2. **同一只票同一天只记第一条。** `record_many` 是无脑追加，而 `advise` 随时能再
   跑，不挡一道，一天跑五次就是五个「独立样本」。留第一条是因为核对流程看的是
   「记下之后价格有没有进入买入区间」，14:50 记的那条只剩十分钟可走。
3. **只记进过裁决层的那些**（`adjudication is not None`）。算不出价位的标的记进来
   会全部落进「规则默认」组，而 `_adjudication_edge` 的 docstring 已经写明：掺进
   没做过决定的样本，差值就被稀释向零。弃权的**要记**，`abstained_samples` 单独
   统计它。

裁决器开不开都要记：不开时 `rule_default` 写下的是规则自己的选择
（`used_fallback=True`），那正是对照组；`--adjudicate` 那些是实验组。两组都要有
样本，这个数才算得出来。

### 14.3 这个缺口能活下来，是因为测试测了两端、没测接缝

`tests/test_adjudication_wiring.py` 的开头写着「三层裁决进台账、进统计、进主链路」，
文件里也确实有「台账」「统计」「主链路」三节——**而「进台账」那节测的是
`from_advice` 本身**（构造一个 advice，调它，断言字段对），「主链路」那节测的是
facts 与盘口。两端各自绿着，中间那根线一根测试都没碰。

补了四条，全部钉**接缝**：`advise` 跑完台账里有没有那一行、跑第二遍会不会变成两行、
`journal=None` 的查询链路会不会误记，以及整条链走一遍（建议 → 核对 → 统计）之后
`by_decider` 落在「规则默认」而不是「未记录」。最后一条是前三条的理由。

### 14.4 第五条口径：删完之后掉下来的那些

第四条清完，`inventory_audit.py` 当场露出**它自己的盲区**：前四条查的全是公开面，
而私有面（模块级 `_func` 与类上 `_method`）**一条自动告警都没有**。§十二 连锁清掉
的那 14 个私有辅助不是扫出来的，是删公开方法时顺手撞见的——没有那次删除，它们
会一直躺着。

补成 `check_private`。两点值得记：

**它能查得准，前四条不能。** `_foo` 按约定只在自己模块里被调，所以引用只在定义它
的那个模块里数就够了，没有跨模块重名顶账的问题——而那正是前四条不得不「宁可漏报
不可误报」的原因。五条里只有这一条可以要求精确。

**它必须迭代到不动点。** 删掉一个私有函数，常常让它调用的另一个也失去唯一调用方；
一轮只能看见第一层。落地当天命中的 3 处正好是两层：`get_l2_quote_raw` /
`get_full_tick_raw`（§14.1 删的）掉下 `_call_optional` 与 `_extract_source_dt`，
后者又独占着 `_first_value`。**一轮扫描会漏掉最后那个**，而漏掉的那个下次没人会
再想起来——§十二 那 14 个就是这么攒的。

`_extract_source_dt` 的测试连同方法一起删了。它钉的浮点卫生（`isinstance(raw,
(int, float))` 会放 `True` 与 NaN 过去）是条好判据，但那条判据的正主是
`numeric.finite`，`tests/test_numeric.py` 已经独立钉住。**教训留在有调用方的那一份
里，不留在没有调用方的这一份里**——否则下一个读到它的人会以为 QMT 还有一条快照
链路。

这一条也顺手改了「什么时候该重跑」这份清单：原来写的是「新增/删除模块、接线、加
字段、加方法」，现在最容易漏的一条是**删掉任何一个函数之后**。删除本身就是制造
孤儿的动作，而它不会有任何告警。

### 14.5 接台账那一刀带出来的一处口径污染

`advise` 落台账（§14.2）解决了「裁决层没有出口」，但它同时往台账里塞进了一类
**此前不存在的记录**：人手点名的标的。这类记录和 `morning` 那批同为
`kind=recommendation`，而 `journal/stats.py` 里有两个函数按 `rec_kind` 取入选组：

```text
_selection_edge   入选组 − 对照组   「这套筛选本身有没有用」
_veto_cost        否决组 − 入选组   「业绩闸门拦错了没有」
```

两个函数的 docstring 都写明差值成立的前提是「**同日、同筛选流程、只差最后一刀
排序**」，而 `advise` 的标的**从来没进过板块排序和业绩闸门**。不隔开的话，分子里
混进一批不是这套筛选选出来的票，`picked_samples` 还会虚高——两个数都会朝着
「看起来更可信」的方向错。

隔开的维度是 `source` 不是 `kind`：`kind` 分的是入选/对照/否决三个**组**，
`source` 分的是记录由**哪条链路**产生。收成 `stats._screened`，只围这两个对照
差值——`advise` 的记录照常进总体统计、按打法分组、按依据类别分组，那几组本来就
不依赖「同源」这个前提。

**这是接线动作的一般代价，值得记一笔**：给一个共享存储加一个新的写入方，等于给
每一个读它的人换了输入分布。台账里当时有 8 个分组函数，其中 2 个的前提被这一刀
打破了——而它们不会报错，只会开始给出偏乐观的数。

## 十五、概念板块进盘前排序

`sectors/intraday.py`（盘中）从 2026-08-09 起就是行业 + 概念两层，盘前
`jobs/morning.py` 一直只有行业。同一套静态分类、同一天，两条链路看到的板块集合
不一样——`INVENTORY.md` §1.1 把它单列成「剩下的缺口」，理由是「接它要改候选池的
产出口径，不是纯增量」。

### 15.1 两层分开排名，各取各的名额

并成一张榜是错的，与盘中那层同一条理由：346 个概念和 31 个行业放进同一张榜，
前者仅凭数量就能包揽前几名——出极值的机会多得多，而那不代表它们更值得做。
所以 `top_sectors`（行业）与 `top_concepts`（概念）是两个独立配额，
`SectorOutlook` 新增 `level` 字段让选择那一步能把两层分开。

选完之后按分数合并排一次序。**这个顺序是有语义的**：`reverse_index`（§14.1）
按「并列时留第一个」把一只票归给它所属板块里最强的那个，而概念接进来之后，
「一只票同属多个板块」从边角变成了常态——每只票平均挂着好几个概念。§14.1 那处
修正因此不是顺手清理，是这一节的前置条件。

### 15.2 三处边界

**成分股取两层的并集。** 概念文件比行业文件多覆盖上百只票（华银电力、华大智造
这类，不是还没归类的新股），只按行业循环会让它们整只消失。`--max-constituents`
的分层抽样反过来**只按行业**分层：概念之间成分股大量重叠，拿它们做分层会让重叠区
的票被反复抽中，而抽样存在的意义正是「板块间可比」。

**重名的概念直接丢掉。** 板块的各层读数（动量、舆情、龙虎榜净额）全部按 `name`
索引，重名会让两层互相覆盖，而覆盖方向取决于字典写入顺序——一个没人声明过、也
没法从代码里读出来的规则。2026-08-10 实测 31 个 SW1 与 346 个概念只撞「家用电器」
一个，丢掉它的代价远小于让一层读数静默错位。

**概念不喂轮动记忆。** `SectorRotationStore` 按 `level` 分档存，而轮动判定比的是
相邻两天**同一张榜**的名次变化。混进去会让「昨天 SW1 前几名是谁」拿到一份两层
掺在一起的名单。

### 15.3 取不到概念要能继续，取不到行业不能

两条失败处置刻意不同：`_concept_definitions` 吞异常并留 note，`_industry_taxonomy`
取不到是要抛的。概念是加进来的第二个维度，静态文件挂掉时盘前照样得出得来一份
只有行业的排序；而没有行业分类，这条链路根本无从开始。

### 15.4 三处构造点收成一个函数，因为 daemon 那处漏了

构造「行业 + 概念」这一对的地方有三处：`cli.py` 的 `morning`、`cli.py` 的 chat
上下文、`jobs/daily_cycle.py` 的 daemon。**接线那一轮 daemon 那处只建了行业**，
于是手工跑 `morning` 有概念维度、无人值守跑没有——而 daemon 才是这套系统真正在
跑的那条路（`INVENTORY.md` §2）。

收成 `sectors/ths_taxonomy.py:static_taxonomies`。它同时钉住第二件事：两层**共用
同一个 `ThsTaxonomySource`**。共用不只是省一次 HTTP——source 的进程内缓存保证两层
看到的是同一份快照，各建一个的话，两次 `load()` 之间上游刷新（实测每天北京 08:00
一次，而盘前跑批就在 08:30 前后）会让行业按昨天的成分股算、概念按今天的算，
而这种错位在产出里看不出来。

daemon 这一处配了**结构守卫**而不是行为用例（真跑一次要连全部外部源）：AST 扫
`morning_task`，断言它既传 `industry_taxonomy` 也传 `concept_taxonomy`，且走的是
`static_taxonomies`。

## 十六、跷跷板：ROADMAP §5.2 最后一个没建的读数

`rotation.py` 建成时落下了 §5.2 的第 2 条。它要回答的原话是「银行和半导体是不是
跷跷板」——而这个问题此前**连数据都没有**：`rotation.py` 算的高低切换是前期涨幅
与近期涨幅的**秩相关**，一个全场一个数的横截面读数，答不了任何一对具体板块之间
的关系。

新增 `sectors/seesaw.py`。输入与 `rotation` / `turnover` 同一批序列、同一个
`panel.align`，三层看的必须是同一张面板。

### 16.1 相关系数必须按**交易日**配对，不能按下标

`panel.align` 保证的是「最后一根是同一天」与「序列足够长」，它**不保证中间那些
天对得齐**：一个停牌三天的板块，清洗掉那三根之后第 60 根往前跨的是 63 个交易日。

这对 `rotation.py` 无所谓（它只回看第 N 根算一个涨幅），对相关系数是致命的：
按下标 zip 会把 A 的周三配到 B 的周一，而**算出来的数看不出任何异常**——它只是
一个偏向 0 的、错的系数。所以日收益按交易日建索引，两条序列先取共同交易日。
用例里同时断言了按下标配会差出多少，那个差值就是这条判据的价值。

### 16.2 固定阈值挡不住多重比较——**这一条是被测试当场抓住的**

第一版是两道闸门：两个半窗同号 + 整窗 ≤ -0.35，多重比较只在 `notes` 里警告了
一句。写「纯噪声不该出跷跷板」这条用例时它当场变红：**231 对互不相关的高斯序列
里，筛出了一对 r=-0.357、两个半窗同为负的「跷跷板」**，两道闸门全放行了。

一句警告挡不住任何东西。改成阈值由 `critical_correlation` 算出来：Bonferroni 把
族错误率摊到每一对上，再经 Fisher z 变换换算成 r 的临界值（只用
`statistics.NormalDist`，不引 scipy）。实测 3240 对时收到 **-0.52**，-0.35 降级成
地板。同一份噪声面板现在报空榜。

**本轮阈值必须跟着读数一起印出去**：它随检验对数变，不写出来的话，同一份榜在
不同天的严格程度是看不出来的。`notes` 里还写明按地板阈值筛、光噪声该出几个。

Bonferroni 控的是「有没有假阳性」，**不是「这个关系明年还成不成立」**。后者要
样本外验证，那要等台账攒够，不是一个算子能给的。

### 16.3 N 对不等于 N 个发现

2026-08-10 实测：通过闸门的 6 对**全部含「银行」**——那是「银行 vs 整个电子链」
一件事，被列成了 6 行。6 行读起来像 6 条证据，而它们全部来自同一个价格序列，
一起对一起错。所以榜上有一个板块占了半数以上的对时，明写这是「一对多结构」。

同一天的另一个结论同样重要：**「银行 vs 半导体」没有通过闸门**。这一层因此把它
报成「历史上没有稳定关系」而不是「无关」——「不在榜上」的含义是「没通过那两道
闸门」，说成「无关」是在替数据下一个数据没给的结论。ROADMAP 原文写着不预设这
一对，这就是不预设的样子。

### 16.4 边界：只解释今天，不外推明天

`explain_divergence` 这个名字就是边界本身。主链路入口是 `explain_today`——它只
解释**榜上**那几对今天真的背着走的，收益取自这一层自己算的那批日收益，不从别处
再取一份：「今天涨跌多少」与「近 60 日相关多少」必须来自同一批序列、同一个交易
日，否则这句话的两半可能落在不同的日子上。

每一句都带着「这是对今天的陈述，不含对明天的判断」。不进打分、不进筛选，处置与
五档、同花顺指数、量价形态、轮动读数完全一致。

## 十七、主链路瘦身：按「这段在不在做判断」切，不按行数切

`jobs/morning.py` 2263 行。**但长不是它的问题**——ruff 的复杂度闸门它早就过了，
六个 `_stage_*` 加起来 649 行，那是真正的判定链路，一行都不该搬。问题在于夹在
判定之间的那些**不做判断的段落**：读主链路的人要连着翻过三百行字典字面量，才能
看到下一个真正在做决定的地方。

所以判据是「这段在不在做判断」，搬走的全是答「不在」的：

| 搬到哪 | 搬了什么 | 行数 | 判据 |
|---|---|---:|---|
| `jobs/morning_facts.py`（新增） | `build_facts` / `market_state` / `equal_weight_date` / `news_source_counts` | ~310 | **纯映射**：每一行都是「读数存在就带上，不存在写 None」，没有一处阈值、没有一处分支会改变结论 |
| `jobs/sources.py`（已有） | 盘前独有的六路可选源 | ~120 | 与该模块已有三个函数**同一个形状**：开关关了 / 适配器造不出来 / 版本对不上 / 取数抛异常，四条都必须落到「这次没有这一项」 |
| `strategy/overnight.py`（已有） | 批量筛选的跨策略重叠与产物拼装 | ~75 | 领域逻辑，与「怎么解析命令行」无关 |

结果：`morning.py` 2263 → **1834**，`_cmd_strategy_screen` 98 → **47**。

### 17.1 那六路源收在一起之后才看得出来的事

它们原来散在两百行判定逻辑中间，六份各自实现同一套兜底顺序。**混在里面时这个
形状是看不见的**——谁也不会发现第七份漏写了一条。收在一起之后，加第七路源时
照着抄就是对的，而这正是 `jobs/sources.py` 那三个函数当初收口的理由，只是当时
只收了 `morning` 与 `post_close` 共用的那三个。

### 17.2 `_cmd_strategy_screen` 98 行，而同文件命令处理器的中位长度是 11 行

**跨档次的那一个，装的通常不是命令而是领域逻辑。** 里面是跨策略重叠、每策略截断、
综合短名单——没有一样和 argparse 有关。搬回 `strategy/overnight.py` 时顺带修掉一处
真重复：`data_notes` 那三行被拼了两遍（单策略分支一遍，末尾一个重复的
`if profile == "all"` 又一遍），两份字面量逐字相同——直到有人只改其中一份。

### 17.3 搬动消费方会静默改变测试的打桩点

`tests/conftest.py` 有三条 autouse fixture，作用是「不显式注入就别去打外网」。它们
补的是**消费模块里的值绑定**（`from ... import default_earnings_adapter` 是一次绑定，
补原件补不到——那条理由 fixture 自己的 docstring 里写着）。

于是把消费方从 `jobs.morning` 搬到 `jobs.sources`，等于把打桩点搬走了。**这次它
炸得很响**（`monkeypatch.setattr` 找不到属性，1198 条全 error），但换一种搬法——
比如两处都还留着同名符号——它会安静地退化成「测试开始打外网」，而没有一条断言
是关于那个站点的。搬动任何一个被 conftest 点名的符号时，先 grep 一遍 conftest。

### 17.4 没有动 `cli.py` 与 `notify/render.py` 的主体

两个文件各 1294 / 1263 行，但**形状已经是对的**：函数中位长度 11 行与 17 行，最长
49 行与 46 行。它们的长度来自「一条命令一个函数」「一个 `## 小节` 一个函数」，
而不是几个巨型函数。再往下拆成 `cli/parsers.py` + `cli/commands.py` 这类，只是把
行数挪到另一个文件，读的人要按住的东西一点没少——**那是搬家，不是瘦身**。
