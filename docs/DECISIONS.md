# 设计决策与被否决的方案

这份文档记录**为什么是现在这样**，以及**哪些看起来合理的方案被否决了、依据是什么**。
写在这里是为了防止后续再被同类方案带偏——被否决的方案通常还会以新的包装回来。

---

## 一、集合竞价拦截：这条路封死了，不是钱的问题

某版「终极实盘闭环」方案的第二层是「09:20–09:25 竞价秒级引擎」。其中两处是
**A 股交易规则层面的逻辑不成立**，不是参数调优问题。

### 1.1 09:20–09:25 不接受撤单，撤单率公式恒等于 0（致命）

错误写法：

```text
R_withdraw = (BidAmount_09:24:30 - BidAmount_09:24:58) / BidAmount_09:24:30
```

A 股集合竞价 **09:20–09:25 期间交易所不接受撤单**。该窗口内买盘挂单量不会因撤单
下降，这个比值恒约等于 0，或只反映价格档位漂移，**无法识别诱多**。

撤单率只能定义在 **09:15–09:19:59** 这个可撤单窗口，且需要数据源提供逐笔委托或
撤单记录——**任何档位、任何数据源都不提供**。

### 1.2 「09:25:02 推送卡片 → 1.5 秒点击下单」在时序上是事后动作（致命）

09:25 集合竞价已经撮合完毕、开盘价已定。09:25:02 才推送，此时下单**无法参与集合竞价**：
沪市 09:25–09:30 不接受申报，深市虽接受但订单只进缓冲区、开盘后才进连续竞价。

这条链路实际产出的是一张 **09:30 的开盘单**，却按「竞价成交」的盈亏比在算，
**会系统性高估收益**。要参与竞价，决策必须在 **09:24:58 之前**完成。

### 1.3 结论：删掉，而不是留着等数据

`engines/auction.py`（221 行）与相关状态机（`AUC_FOCUS` / `AVOID_NOFILL` /
`AVOID_FAKE_STRENGTH`）已一并删除。它实现的是一个**用不存在的数据、在来不及的时刻
做出的决策**。

即使接上 QMT 也补不上：QMT 给的是券商侧五档与逐笔成交，**不是交易所的竞价撮合量与
未匹配量**。那个数据交易所根本不发布。

> **留下的教训**：在没有 L2 之前，竞价相关字段一律置空并标 `data_stale`，
> **不要用日线数据凑数**——把全天成交额填进 `matched_amount`，会让日线数字轻松通过
> 为竞价设计的三千万门槛。

## 二、四个会静默出错的公式

这些不是「不够精确」，是**在最需要它们的时候方向反号**。

### 2.1 `R_unmatched = Unmatched / Matched` 无上界

Matched 很小时该值可以是几十、几百，`> 60%` 的阈值失去意义。

正确形式，值域锁死在 `[0, 1]`：

```text
R_imbalance = Unmatched / (Matched + Unmatched)
```

### 2.2 `R_tail = NetInflow_last30m / NetInflow_total` 在净流出时符号翻转

全天净流出（分母为负）时比值符号翻转——**尾盘也在流出的票会算出正的大比例，
尾盘拉升的票反而算出负值**。这个判据在下跌市（恰恰最需要它的时候）会系统性误判。

正确做法：加方向门槛，仅当 `NetInflow_total > 0` 时才判定；否则标记为未定义、
不参与打分。

### 2.3 `F_market_emotion` 在 N=50 处不连续

分段函数在 `N_down = 50` 处从 `1.0 - 35/50 = 0.3` 直接跳到 `0.1`。**跌停 50 家和
51 家的市场状态几乎相同，仓位上限却差 3 倍**；盘中跌停家数在 50 上下反复穿越时，
仓位指令会来回翻转。

正确做法：连续段保持线性平滑，熔断做成**带滞回的独立开关**（进入阈值 55、退出阈值 45），
不要让熔断以断点形式混在连续函数里。

**这条已经推广成全系统的原则**：阶跃函数在阈值两侧给出差很多的分，而阈值本身是
拍脑袋定的，读数在附近来回穿越时排序就会抖。现在大盘层与个股层都用斜坡
（`_ramp(value, onset, full)`）。

### 2.4 `强度 = 命中密度` 在小样本上方向反了

板块舆情用 `intensity`（命中密度）加权时，**样本越小平均密度越高**。实测出现过
基础化工靠 2 条快讯拿满 +12、计算机 22 条只拿 +2.0。

正确做法：文档数不足 8 条时按 `条数/8` 折权。密度是密度，证据量是证据量。

## 三、C++/Cython 极速引擎 + 盘后冷编译：过度工程

方案要求「30ms 内纯原生算术校验」并配套「15:30 冷编译 C++ 引擎」。

**瓶颈从来不在算术**：几百只标的的比值运算在 CPython 里是亚毫秒级。真正的延迟在
数据源——TickFlow 是 REST 快照（百毫秒级往返），券商 L2 推送也在几十毫秒。

为占比不到 1% 的环节引入 C++ 工具链和每日编译流程，换来的是运维负担和一条**无法热修
的关键路径**。

**保持纯 Python。**

## 四、威科夫：借概念，不借体系

这个项目借用威科夫的**结构概念**作为一层轻量覆盖，不是完整的自由裁量交易体系。

**保留**：吸筹/派发倾向、Spring 与 Upthrust 识别、SOS/LPS 确认、
effort vs result、压缩后扩张。

**丢弃**：重量级 agent 编排、策略膨胀、把不透明的 prompt 当主决策层。

**在本项目里**：

- `WyckoffAnalyzer` 把历史 bar 打成结构倾向
- `DailyTechnicalAnalyzer` 抽支撑、压力、趋势状态、形态提示
- 结果只用于研究，不下单

**转向低吸口径之后，威科夫的权重重排过一次**：

| 事件 | 原权重 | 现权重 | 理由 |
|---|---|---|---|
| MARKUP（主升段） | +12 | **+7** | 主升段是**追高**的位置 |
| ACCUMULATION（吸筹末端） | +10 | +10 | 低吸该待的地方 |
| Spring（假跌破收回） | +6 | **+8** | **就是低吸信号** |
| LPS（回踩承接） | +4 | **+7** | **就是低吸信号** |
| SOS（放量上推突破） | +5 | **+3** | 强势确认，对追涨有用，对低吸是「已经晚了」 |

**阶段本身只说明「趋势没坏」，真正的进场信号是事件。** 原来的排序把追高排在了回踩前面。

用法：当交叉验证，不当唯一真相来源。

## 五、「持续学习」不做成在线学习

样本量不够时的在线学习就是过拟合。

**不做的**：拿几十个样本拟合出来的、看起来在学习的东西。

**做的**：记账 → 对照组 → 兑现核对 → 统计，**只到这里为止**。上模型的触发条件是
台账里有 **200 条已兑现记录**（`journal/stats.py:MODEL_READY_SAMPLES`），
不是「攒了两周」。在那之前统计只报告、不回写任何权重。

### 为什么必须有对照组

没有负样本就永远回答不了「**筛选规则本身有没有用**」。入选组次日涨 1.2% 听起来不错，
但若对照组涨 1.4%，这套规则就是**负价值**。

对照组取**紧邻落选**而不是全市场垫底——后者差出来的是「好票 vs 烂票」，不是规则的价值。
等量是为了让两组的统计噪声量级可比。

### 为什么必须存当时的大盘状态

同一套规则在退潮期和启动期的期望值可以是**反号**的。不把炸板率、最高连板、涨跌停家数
和大盘读数存进每条记录，事后就无法按情绪周期分层。

**冗余存储是刻意的**：台账是 JSONL，每条多带七八个数比事后按日期 join 便宜得多，
而且**记录自带分层维度**意味着任何一段区间的数据都能独立分析，不依赖别的文件还在不在。

### 为什么两套持有期口径并存

`next_open/high/low/close` 对应「次日就卖」，五日 MFE/MAE 对应低吸的自然持有期。
**哪种更合适现在拍板都是猜，两个都记让数据回答。**

隔夜跳空单独记，是因为持仓过夜的收益里它常常比日内择时贡献更大，混在 MFE 里就归因不出来。

### 特征必须在采集之前定好

台账字段一旦漏了，之前的样本就**永久失去分层能力**——两个月后才有足够样本回答
「回撤 5% 买和回撤 8% 买哪个次日溢价高」，那时再想补字段已经晚了。

所以 `signals/dipbuy.py` 只负责**算出这些数**，不负责打分：打分口径还在观察期、随时会调，
特征定义不该跟着抖。

## 六、买卖点：为什么是「候选集 + 裁决」而不是两个极端

### 全部写死是错的

那些阈值——回调 5% 算深、量比 1.0 算放量、盈亏比 2.0 达标、买入区间 = VWAP ± 12%
日振幅——**没有一个是拟合出来的**。它们看起来精确，实际是一组从未被验证的猜测，
而且用一个数掩盖了「这里本来有多个合理答案」这个事实。

### 全交给模型也是错的

同一份数据两次调用会给出不同的价，而且回答不了「为什么是 22.95 不是 22.80」。
台账里记下来的东西因此无法归因，整个持续学习的链条断掉。

### 所以分界线画在「谁能产生数字」和「谁能做取舍」之间

- **规则产生所有数字，并给出一组带出处的候选**（含自己的默认排序）
- **模型只在候选集内做取舍**，必须引用 L1 读数说明理由，可以弃权，**不能造价**
- **数字闸门比通用闸门更严**：价格必须**恰好等于**某个候选，不接受近似匹配
  ——22.95 和 22.96 在文本比对里都能过，但那是两个不同的挂单价
- **LLM 挂了就取默认排序**，链路照跑

### 这个决定本身也要被验证

台账**同时记录规则默认与模型裁决两套结论**，兑现核对对两套各算一遍。
「加了裁量权有没有用」因此是一个**有数据能回答**的问题。

在样本够之前，这条记录在文档里：**给模型裁量权是因为写死的阈值同样没有依据，
不是因为有证据说模型更好。**

## 六b、为什么是「周期闸门 + 打法分支」而不是继续调权重

上一轮把打分口径从追涨转成低吸，改的是**权重的符号**（MARKUP 12→7、缩量从 −5
改成正分、阶跃换斜坡）。2026-08-03 的实盘输出说明那一轮没修完：

```
60 条建议  →  54 条只是 shallow 回调、52 条是**放量**回调、0 条下跌趋势
当日炸板率 51.94%（系统自己的定义里 ≥50% 即退潮），仓位系数照给 0.68
```

### 继续调权重解决不了

缩量在打分里占 ±6 分，而 trend + wyckoff 占 50。把缩量加到 ±20 也压不过
「趋势强 + 威科夫结构好」的组合——**只要它是权重，就可以被别的项买回来**。
这和 §六「全部写死是错的」不是同一件事：那里说的是阈值该不该由模型取舍，
这里说的是**某些条件根本不该参与加权**。

「回调放量」不是一个减分项，它是「这不是回踩」的定义。定义必须是门槛。

### 同一条教训第二次被应用：业绩不进打分

2026-08-04 接入业绩预告层（`adapters/earnings.py`）时，这条结论被**原样复用**，
并且真的挡住了一次重犯：

开发过程中一度出现 `_score_earnings` 给 `is_strong_catalyst` 加 **±6 分**——
和上面那个缩量的数字**一模一样**。它看起来很有道理（中报预增 +1197% 的票凭什么
和普通票同分），但没有任何回测支持这个幅度，而它一旦是权重，就会在
「趋势强 + 威科夫好」的组合面前被买回来，同时又足以在别处把一只本不该入选的票
顶进候选。

**最终口径是双面不对称的：**

| | 处置 | 为什么 |
|---|---|---|
| 亏损 / 大幅预减 | **门槛**，打分前移除标的 | 「中报窗口内在亏钱」是一个定义，不是一个程度 |
| 预增 / 扭亏 | **只进理由、台账、简报措辞，不产生分数** | 未经回测的正向读数一律先落台账 |

`_score_earnings` 因此返回 `None` 而不是 `0.0`，`EARNINGS_CAP` 常量被删除而不是
设成零——一个存在的上限常量迟早会有人把它接回 `total`，而返回 `None` 的函数
没法被 `total +=` 用上，改回去必须是一次**显式的、看得见的**改动。

### 否决必须留下可核对的痕迹

业绩门槛是这套系统里唯一一道**明知有代价还是加了**的闸门：它会挡掉亏损但正当红
的题材股，而那在超短线上完全可能是当期最强的品种。

所以它必须自带账单。台账新增 `KIND_VETOED` 一类，被否的标的按同一套兑现流程核对
（参考价从板块动量已取的日线里拿，零额外请求），`journal/stats.py:_veto_cost`
算「否决组 − 入选组」。**正数意味着这道闸门在帮倒忙。**

这和对照组（`KIND_CONTROL`）问的不是同一件事：对照组问「排序有没有用」，
否决组问「这道闸门拦对了没有」。后者此前根本无法回答——被否的标的在打分之前就
消失了，台账里连名字都没有，于是代价只能停留在设计者的自述里。

范围限定在**被选中板块内**的否决对象：全市场 284 家首亏与这次筛选无关，记进来
会让两组不再同源，差值就不再是这道闸门的代价。

### 同一份裁决在两条链路上强度不同

`morning` 否决，`advise` 只置顶警告。这不是不一致，是**「谁在提问」不同**：
前者是系统主动从几千只里选，后者是你点名问一只票——「这只票我不给你看」是最没用
的回答。ST 筛选已移除；这条不对称口径现在只适用于业绩否决。

### 被否决的两个替代方案

**只加一个「今天别做」的开关。** 最省事，但它只解决炸板率那一个问题，回答不了
「上涨趋势什么样的可以买」。而后者是这套系统从来没有能力表达的东西——趋势一直
是权重，权重表达不了「不同趋势走不同判据链」。

**直接上机器学习/因子模型。** 现在台账只有 2 个交易日、0 条已兑现。没有回测
基线的情况下，ML 只会更快地过拟合到这两天。**顺序必须是先有分支、再有回测、
最后才是模型**——反过来做，模型学到的是当前这套有缺陷门槛的输出分布。

### 为什么闸门的切点和台账分层共用一组常量

`journal/stats.py` 现在从 `strategy/regime.py` import 切点。两边各定一套是个
隐蔽的坑：闸门按 0.50 切、统计按 0.55 切，那么「退潮期这套规则管不管用」的样本
就和**真正被闸门拦下的那些日子**对不上，闸门永远无法被自己的台账验证。

改造前恰好就是这个状态——`stats.py` 用 0.30/0.50，`sectors/predict.py` 用
0.25/0.55。后者是连续斜坡（另一种数学对象）所以保持独立，前两者已统一。

### 情绪周期的判定存标签，不是只存原始读数

台账 `market_state.regime` 存的是**当时闸门实际判定的那个标签**，统计分组优先
读它、只有老记录才回退到用炸板率现算。理由同上：分组必须和当时生效的判断一致，
否则改一次阈值就会让历史样本重新分组，而那些样本对应的是旧阈值下的行为。

## 七、其余已固化的决定

| 决定 | 理由 |
|---|---|
| **筛选与打分分离** | ST、退市、立案调查这类风险无法被好走势补偿，做成扣分迟早被其他因子的正分盖过 |
| **没数据 ≠ 中性** | 给中性默认分会让「无知」压过「测量出的走弱」 |
| **数据缺失时放行而非拦截** | 用「没测到」当否决理由，等于让数据缺失冒充风险判断 |
| **越紧急的输出越不经过 LLM** | 盘中告警秒级时效，LLM 增加 2–5 秒延迟与一次失败可能 |
| **合规文本程序化追加** | 实测 Qwen 在被明确要求保留时，仍会在概括中整段丢掉风险提示 |
| **按跃迁告警而非按状态** | 145 轮/天，按状态告警到中午就被静音了 |
| **止损每日只发一次** | 反复穿越止损位时连发五条，人只会把通知静音 |
| **止损与目标开盘 15 分钟后钉死** | 每轮重算的止损永远在当前最低价下方，`stop_break` 结构上无法触发——跟着价格往下走的止损不是止损 |
| **自选股/候选池/热门股三个列表分开**（热门股 ⬜ 未建） | 混在一起就分不清哪些是自己决定要盯的、哪些是机器刚塞进来的 |
| **热门股不进台账**（⬜ 未建） | 入选条件随盘中情绪变，混进去会污染「盘前筛选有没有用」的样本 |
| **同花顺行业指数不参与打分** | 90 个行业 ≈ 申万二级粒度，硬映到一级只会造出假精度 |
| **五档只做有界旁证** | 挂单可撤可假挂且只有五档；当主判据等于把仓位押在别人随时能撤的单上 |
| **裁决器输出 key 而不是价格** | 提示词说「不许编」是请求不是约束；只给「指一个已有的数」的通道才是约束 |
| **弃权是一等公民** | 规则层永远能算出价位，表达不了「今天不该买」——那是裁决层最有价值的增量 |
| **裁决器不进盘中循环** | 每标的一次 LLM 调用，20 只票 = 20 次往返、二十个失败机会，而告警要秒级 |
| **规则默认无条件进候选集** | 否则闸门会把引擎自己报的价判成越界，且台账两个字段静默对不上 |
| **挂单墙门槛按当日成交额缩放** | 固定金额在 3 元的票和 1350 元的票上无法同时成立 |
| **委比在涨跌停上单独标退化** | 恒等于 ±1.0，混进排序会让买不进的涨停票永远排第一 |
| **分片取数失败就抛错且不写缓存** | 宁可跑不出来，也不留一份不知道完不完整的分类 |
| **语料库用 SQLite，其余用 JSON/JSONL** | 它是唯一需要按板块/标的/时间窗**查询**且长期累积的数据 |
| **不产出概率/胜率/预期收益率** | 没有拟合模型能支撑它们 |

### `screening/` 的移除与它留下的那个读数

该模块用三档口径拆解「昨日低点到次日高点差 2%，就在低点买」这类筛选条件：
`oracle`（T 日最低买 / T+1 日最高卖，**上帝视角，做不到**）、`neutral`（收盘买 /
次日均价卖，不择时）、`strict`（收盘买 / 次日开盘卖，完全机械）。

2026-08-01 取 25 只两年日线、成本按 0.202% 往返扣除：

| 读数 | 结果 |
|---|---|
| `oracle` 中位数的中位数 | **1.91%** |
| `neutral` 中位数的中位数 | **-0.20%** |

**那 2% 几乎全部是择时溢价，不择时的话是负的。** 模块本身已移除，但这个读数
必须留下来——它是对「找波动大的票就能赚」这个直觉最直接的反驳，而且它解释了
为什么这套系统把力气花在**判断买卖点**而不是**筛选标的**上。

## 九、这一轮建三层时发现的两个静默缺陷

两个都属于「不会报错，只会悄悄变成另一件事」，都不是这次改动引入的。

### `/debate` 每一次调用都抛 TypeError

`chat/session.py` 里写的是 `session.has_facts()`，而 `has_facts` 是 property。
调用它等于去调用一个 `bool`。上下文空不空都一样炸——空的时候 `not False` 先求值，
`False()` 照样抛。

它活下来的原因值得记：**辩论层本身测过四条，但从对话入口进去的那条路一条都没有。**
测了「零件能转」不等于测了「装上去能转」。修复只有一个括号，补的测试才是重点。

### 五档快照的量纲取决于是哪个源答的

`Snapshot` 一个 `volume` 字段，新浪填股、腾讯填手。此前没有消费者同时用两个源，
所以没炸；这次要把五档接进买卖点，两边的挂单量要放在一起比，差 100 倍会让挂单墙
判定完全失效——而且不会报错，只会给出一个错误的价位。

同一个数据类承载两个源时，**量纲契约必须在解析层就统一**，不能留给下游。

### 顺带关掉的一类测试泄漏

`OrderBookAgent` 在没拿到 adapter 时会自己构造一个真的 `SnapshotAdapter`——生产
里这是对的，测试里这是一次静默外网请求。实测每个 `run_advise` 测试都在打
`qt.gtimg.cn`，只是网络快，看起来像没打。

和 `conftest.py` 里那条凭据泄漏同源：断网的机器上它变成几秒超时，网络好的机器上
它让测试依赖一个第三方站点的可用性，而没有任何一条断言是关于那个站点的。现在
默认源在测试里被钉成 `None`，要测五档的测试自己注入。

## 十、这一轮全仓清理：把复制出来的东西收成一份

清理的判据只有一条：**同一件事在几个地方各写了一份，而每一份都略有不同**。
重复本身不贵，贵的是每一份漏掉的那一项都不一样，于是缺陷只在其中几条路径上出现。

### `numeric.py`——九份 `_float` 收成一份

仓库里有九个数字收口函数（`_float` / `_number` / `_num`），没有两份的判据是一样的：

| 变体 | 挡空串 | 挡 `"-"` / `"null"` | 挡 NaN | 挡 ±inf | 挡 `bool` |
|---|---|---|---|---|---|
| `limit_pool` / `sina_intraday` | ✗ | ✗ | ✓ | ✗ | ✗ |
| `market_scan` / `tickflow_market` | ✓ | ✓ | ✗ | ✗ | ✗ |
| `validate` | ✗ | ✗ | ✓ | ✓ | ✓ |
| `dipbuy` | ✓ | ✗ | ✓ | ✗ | ✗ |
| `snapshot` | ✗ | ✗ | ✗ | ✗ | ✗ |

**没挡 NaN 的那几份是真的风险**：NaN 不会抛异常，它会一路参与比较，而 NaN 的比较
恒为 False——「跌破止损」于是静默变成「没跌破」。现在统一成一条判据：能变成有限
实数就要，否则一律 `None`，下游只判 `is None`。

`snapshot` 那一份额外把 `0.0` 当缺失（停牌时行情源回 `0.00`），保留为
`positive()`；它同时也挡掉了负价，比原来的「非零即可」更严。

另有五份「按几个字段名依次试」的变体收成 `first_finite()`。

### 另外三处逐字重复

| 收到哪 | 原来散在 |
|---|---|
| `schedule/clock.py::minutes_since_open` | 三个适配器各一份。算的是**市场规则**（午休那 90 分钟要挖掉，否则量比系统性偏低四成），不是某个源的解析细节 |
| `advice/view.py` | `ask/context.py`、`chat/session.py`、`monitor/triggers.py` 各写了一份排序键、换手率/成交额拼接、买入区间格式化。漂移的后果是同一只票在 `ask` 里排第一、在 `chat` 里排第四，而两边读的是同一个 JSON |
| `notify/base.py::publish`、`adapters/snapshot.py::default_snapshot_adapter` | `monitor/loop.py` ↔ `schedule/daemon.py`、`agents/collectors.py` ↔ `jobs/monitor.py` |

### 再一轮扫出来的四处

| 收到哪 | 原来散在 | 重复之外的代价 |
|---|---|---|
| `adapters/base.py::security_names` | `jobs/morning.py`、`jobs/post_close.py`、`monitor/session.py` | 无。纯展示字段，三份行为一致 |
| `adapters/base.py::fetch_daily_bars` | 同上三处 + `journal/verify.py` | 哪天多一个源支持 `get_historical_bars_batch`，改一处改不全，剩下三条路仍逐只打——只表现为「慢」，不表现为「错」，因此不会有人报 |
| `jobs/progress.py::progress_reporter` | `jobs/morning.py`、`jobs/advise.py` | 无。但收口之后「进度回调永不抛」这条约束有了单一落点 |
| `signals/series.py` | `signals/dipbuy.py`、`signals/volume_price.py` 各一份 `_series` / `_change` / `_mean` | **已经分叉了**：`volume_price` 那份走 `numeric.finite`，`dipbuy` 那份还是裸 `float()`。一个 NaN 收盘价在低吸判定里能穿过去（NaN 的比较恒为 False，「跌得够深」静默答否），在量价画像里却被挡住——同一个读数，两条链路两个结论 |

### `cli.py`：一条 if 链和一段两百行的顺序代码

两处都不是「逻辑复杂」，是「一个函数里塞了十六份互不相干的东西」——
`PLR0915` 数出来的 139 条语句里没有一个分支。

| 原来 | 改成 | 为什么值得动 |
|---|---|---|
| `main()` 里 16 段 `if args.command == "X": ... return` | `COMMANDS` 表 + 每条命令一个 `_cmd_*(args)` | 分支之间没有任何共享逻辑，它们只是碰巧写在同一个函数里。拆开之后每条命令能单独调用和测试，`main` 只剩「取参数、查表、执行」三行 |
| `build_parser()` 220 行顺序 `add_argument` | 每条命令一个 `_parser_*(subparsers)` | 加一条命令 = 加一个函数 + 加一行，而不是往两百行里再插十行 |

`main()` 原来的 16 个 `return` 现在由字典查表替代。**没有加 fallback**：
`subparsers` 是 `required=True` 的，命令名一定在表里；真取不到就让 `KeyError`
抛出来——那种情况是接线漏了一条命令，不该悄悄什么都不做。

改动本身零风险，但验证方式值得记：把 `build_parser()` 的**全部** subcommand、
flag、default、choices、help 序列化成 JSON，改前改后 `diff` 为空。argparse 的
接线错误（少一个 flag、default 变了）不会让测试红，只会让某个开关某天不生效。

### `tabular.py`——`numeric.py` 的另一半

`numeric.py` 管**单元格里的数**，这个模块管**表的形状和单元格里的字**。同一件
事的两半：akshare 这类源有时给 `DataFrame`、有时给 `list[dict]`、拿不到时给
`None`，每个适配器都得先把三种情况抹平才能开始干活。

六个文件各写过一份，其中**三份逐字相同**（`earnings._records`、
`sina_intraday._rows`、`akshare_source._rows`），已收进 `records()`。

真正值得记的是 `text()` 挡掉的那三个字符串：

```python
"nan"  "none"  "nat"     # pandas 把缺失值 str() 之后的样子
```

**它们会通过所有非空判断。** `bool("nan")` 是 True，`title or "无标题"` 拿到的
是 `"nan"`。一条没有标题的公告，标题字段会变成字符串 `"nan"` 并一路印进简报——
不报错，只是简报里多一行 `nan`。和 `numeric.py` 挡 NaN 是同一类问题：**必须在
解析层变成缺失值，因为下游判的是 `is None`，而这三个都不是 None。**

`akshare_adapter` 与 `tickflow_adapter` 那两份没有并进来：前者把非 dict 元素
包成 `{"value": item}`，后者要处理紧凑 K 线载荷，语义确实不同。
`chip_distribution` 那份自带 `try`（「取不到就当没有筹码数据」），也留着。

### `PLR0911` 的阈值：把 6 提到 10，而不是去改代码

`ruff` 默认允许一个函数有 6 个 `return`。全仓 1168 个函数里超过 6 的只有
**1.5%**，逐个看过之后**没有一个是「一个函数干了两件事」**，全部是两种形状：

| 形状 | 例子 | 为什么 return 多是对的 |
|---|---|---|
| 分档判定阶梯 | `wyckoff._classify_bias` | 评分映射到 7 个结构档位，**顺序本身是语义**（前面的规则覆盖后面的）。改成查表就丢掉了覆盖关系 |
| 类型分发 | `qmt_xtdata._to_plain` | 要认 numpy 交出来的 8 种形状，有几种形状就有几个 `return` |

两种都是卫语句风格，摊平比嵌套好读。**这条规则在这里罚的是正确的写法**，所以
调阈值而不是改代码——`max-returns = 10`。10 不是照着现状凑的数，是「一次分发
或一条阶梯」的天花板：再多基本意味着在两个维度上同时分发，那才是该拆的信号。

分支数与语句数超标的那几个走 `per-file-ignores`，并且和早先那四个**分开列**：
前四个是「以后要拆」，后加的六个是**已经看过并决定不拆**（`monitor/loop.py` 的
5 份循环状态、`daily_technical.py` 的 SVG 坐标计算、适配器的字段兜底、审计脚本
的线性过程）。两类欠账混在一张名单里，过两个月就分不清哪些还欠着。

至此 `ruff check .` 全仓退出码为 0，这道闸门可以进 CI 了。

### 顺带修掉的一个闭包

`jobs/morning.py::_record_journal` 在 `for item in candidates` 里定义 `pct()`，
闭包捕获的是**循环变量** `reference`。今天没出事，只因为它每轮都立刻调用；
只要有人把调用挪出循环（比如攒起来批量算），所有记录会一起用上最后一只票的
参考价——**不报错，只让台账里的百分比整体偏掉**。提为模块级
`_pct_against(value, reference)`，参考价变成显式入参。

### 顺带修掉的一个 NameError

`chat/session.py` 的 `_render_generic_summary` 调用了一个**在该模块里不存在**的
`_short()`——函数是从 `ask/context.py` 抄过来的，抄漏了它依赖的那个助手。
`/show` 只要遇到「不带 symbols 的 bundle」或「非 dict 的 bundle」就抛 `NameError`。

和 §九那条 `/debate` 同一个成因：**抄过来的代码没有被抄过来的测试覆盖**。

### 留下来没动的一处：`wyckoff.py` 的 EXHAUSTION 打分

```python
score -= 8.0 if close_position >= 0.5 else 8.0
```

两个分支都是 `8.0`，所以 `close_position` 这个判据是**死的**。邻近的 ABSORPTION
写的是 `+8.0 if ... else -8.0`，对称地看原意应该是
`-8.0 if close_position >= 0.5 else +8.0`。

**没有改。** 改它会直接改动评分输出，那是口径决策不是清理；而且没有任何一条测试
覆盖这个分支，改完也没有东西能告诉你改对了。已在代码里标注。

### 为什么把 ruff 配置写进 `pyproject.toml`

裸跑 ruff 在本仓库报 438 条，其中 5384 条候选是 `RUF001/2/3`（中文全角标点被当成
「可能打错的 ASCII」）、97 条是 `BLE001`（宽捕获——那是**架构决定**，见
`agents/base.py`）、177 条是 `DTZ`（naive datetime——全系统只有一个时区）。

这种信噪比下没人会看第二次。现在显式列出规则族并逐条写明为什么忽略，
`ruff check` 的产出降到个位数，是一道能用的闸门而不是一堵墙。
