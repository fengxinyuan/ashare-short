### 2.1 「每次调用都稳」不等于「链路能跑完」——TickFlow 有硬闸门

**测于 2026-08-02。** 上表每格测的是**单次调用**，永远碰不到配额。盘前全链路一次要打：

| 阶段 | 调用次数 |
|---|---|
| 申万 SW1 分类（335 个分片，冷启动） | 335 |
| 板块动量（4430 只 / 100 一批） | 45 |
| 候选股 240 日历史 + 标的信息 | ~15 |

**实测闸门：60 次 / 滚动 60 秒，第 61 次必定 429。** 而 60 次只花 22.5 秒——
按自然节奏打，配额会以 **2.7 倍速**烧光。错误消息里带服务端自报的等待时长
（`请 38266ms 后重试`），比任何本地猜测都准。

后果是**两个都不响的故障**：`morning` 跑到候选股取数时直接崩；更糟的是分类层把异常
吞成空成分股，**残缺的分类被写进缓存**（3961/4430 只，静默少 469 只，31 个行业一个
不少，文件外观完全正常）。

**已修**（`adapters/ratelimit.py`）：客户端滑动窗口令牌桶（默认 55/60s，
`TICKFLOW_RATE_LIMIT` 可覆盖）+ 撞墙后按服务端等待时长退避。闸门包在 SDK client 上
而不是适配器方法上——`taxonomy.py` 拿的是 `adapter.client` 直接调 `universes.*`，
包方法覆盖不到那条路径。

| | 修复前 | 修复后 |
|---|---|---|
| 连打 80 次 `universes.get` | 第 61 次 429 崩 | 80/80 成功，66s |
| SW1 分类冷启动 | 3961/4430（静默缺片） | **4430/4430，0 分片失败**，363s |
| `ashare-ds morning` 全链路 | 崩在 `_rank_candidates` | **跑完，72s（缓存命中）** |

## 三、不可用的源：是本机网络策略，不是数据源问题

**这条对付费决策最关键。**

所有域名都解析到 `198.18.0.x`（保留网段）——本机在**出口代理白名单**后面。TCP 443
能连上（代理接受），但目标不在白名单时代理直接重置连接，这正是 `RemoteDisconnected`
的成因：

```
curl push2.eastmoney.com/api/qt/clist/get    → http=000   （代理重置）
curl push2ex.eastmoney.com/getTopicZTPool    → http=200   ✅
curl hq.sinajs.cn/list=sh600519              → http=200   ✅
```

| 主机 | 状态 | 影响的接口 |
|---|---|---|
| `push2.eastmoney.com` | ❌ 被拒 | 批量行情、五档盘口、板块列表、efinance 全部 |
| `push2his.eastmoney.com` | ❌ 被拒 | 分钟线、日线 |
| `push2ex.eastmoney.com` | ✅ 通 | 涨停池/炸板池/强势股池（`stock_intraday_em` 逐笔仍 0/8） |
| `datacenter-web.eastmoney.com` | ✅ 通 | 龙虎榜、北向 |
| `hq.sinajs.cn` / `qt.gtimg.cn` | ✅ 通 | 五档、快照、涨跌停价 |

**所以：**

- 不存在「重试能救活」的可能——这是网络策略，不是抖动或限流。
- **换到本地或国内云主机，东财全系大概率复活。**「东财已死」是**本机结论，不是数据源结论**。
- 因此：**不要为了绕开本机网络限制去买付费数据源**——那是花钱买错东西。先换部署环境验证。

> 诚实记录：16:46 单次探测中 `stock_zh_a_hist`、`stock_individual_fund_flow`、
> `stock_market_fund_flow`、efinance 全市场快照曾各成功一次；随后 8 轮受控复测 0/8。
> 按不可用处理。

**经验法则：`push2*` 上的任何东西在本机都不可用。** 系统不依赖它们——板块行情从成分股
日线聚合，分钟线来自新浪，五档来自新浪/腾讯。

## 四、付费档（TickFlow Pro，¥99/月）实测

主机 `api.tickflow.org`（免费档是 `free-api.tickflow.org`，是**两个不同的 host**）
解析到 `198.18.0.50`，返回 401 正常鉴权响应而不是连接重置——付费主机在本机出口代理
白名单内，**这是付款前唯一必须确认的事**（东财 `push2` 就是死在这一层）。

**代码零改动**：`export TICKFLOW_API_KEY=...` 即可，`mode` 自动切 `full`，
能力位翻 `True`，`wrap_client()` 对付费 key 自动退化成透明代理。

### 4.2 批量接口——付费档最被低估的部分

| 操作 | 免费档 | 付费档 | 倍数 |
|---|---|---|---|
| 申万分类冷启动（335 分片） | 335 次串行，受 60/min 节流 = **6 分 16 秒** | `universes.batch` 2 次调用 = **1.58 秒** | **≈240×** |
| 全 A 行情 | 新浪 56 页并发 5.3s | `quotes.get(universes=['CN_Equity_A'])` 0.7s | 7.5× |
| 全 A 标的元数据 | 腾讯逐只 | `instruments.batch` 5534 只 / **0.97s**，涨跌停价 **100% 覆盖** | — |

最后一行解掉了一条长期已知边界：`strong_count` 此前用「涨幅 ≥ 9.5%」近似涨停，
分不清主板 10% 与创业板/科创板 20%。实测宁德时代涨停价 482.26（20%）、平安银行
12.77（10%），两档区分正确。**该判据尚未改用真实涨停价**——它直接喂板块打分，
换判据会让历史分数不可比，须连同阈值重标定一起做。

### 4.3 分钟 K 线的两个硬边界

**单次 5000 根封顶。** `count` 传 5000/10000/20000 返回的都是 5000 根，配 `start_time`
也一样——服务端给的永远是 `end_time` 之前最近的 5000 根。要更早的数据只能**把
`end_time` 逐段前推**，见 `adapters/tickflow_intraday.fetch_minute_history`。

| 周期 | 单次上限 | 覆盖 | 数据底 |
|---|---|---|---|
| 1m | 5000 根 | 21 个交易日 | 翻页可达 **2025-05-23** |
| 5m | 5000 根 | 104 个交易日 | 2025-05-23 |
| 15m / 30m / 60m | 4648 / 2324 / 1162 根 | 291 个交易日 | 2025-05-23 |

翻页实测：600519.SH 1m 拉满 12 个月 = **58322 根 / 242 个交易日 / 5.5 秒 / 12 页**。

**这是「未经回测」第一次具备解除条件。**

### 4.4 两家的分钟线并不逐根相同

量纲对齐之后，TickFlow 与新浪重叠的 1970 根 1 分钟线里完全一致的只有 **39%~61%**，
相对差中位 ~1e-4、最大 **0.15%~0.31%**（不同厂商把逐笔归并到分钟的边界处理不同，
不是谁错了）。

含义：换一条路会让价位漂移最多约 0.3%。**不要把两条路的读数混进同一次计算，
也不要拿一条路的历史去回测另一条路要跑的规则。**

## 五、量纲陷阱与校验

**这一节是错了不会报错、只会算错的地方。** 每一条都有测试钉住
（`tests/test_tickflow_market.py`、`tests/test_tickflow_intraday.py`）。

| 字段 | TickFlow | 新浪 | 错了会怎样 |
|---|---|---|---|
| `volume`（行情与分钟线） | **手** | 股 | 差 100 倍。`_vwap` 用 `amount/volume`，不换算茅台 VWAP 算成 135083 而不是 1351 |
| `ext.change_pct` | **比值**（-0.0082） | 百分数（-0.82） | 差 100 倍 |
| 流通市值 | 需自算 `float_shares × 现价`（元） | `nmc`（**万元**） | 不归一则 20 亿门槛变 20 万，可交易性筛选静默失效 |

**浮点卫生。** 复权后 OHLC 四个字段各自带尾巴，实测 60 只 / 15000 根 1 分钟线里
**1399 根（9.33%）满足 `high < low`**（量级 1e-13）。下游拿 `high - low` 当振幅、
拿 `low == min(lows)` 找枢轴点，倒挂会静默出错。取到 4 位小数后归零。

### 校验层做什么

`adapters/validate.py` 把上面这些做成可复用的检查，而不是散落在各调用点：

| 检查 | 方法 | 失败时 |
|---|---|---|
| 跨源交叉 | 两路都有的字段逐个比 | 出 note，**不改数** |
| 量纲 | 从 `amount / volume` **反推**单位，不查配置 | 推不出来就拒绝算 VWAP |
| 浮点卫生 | `high < low` 倒挂 | 取 4 位小数；仍倒挂则交换并计数 |
| 日线 ↔ 分钟线 | 同一交易日收盘价之比（`advice/engine.py`） | 落在 `[0.2, 5.0]` 外即判定对不上，**不给价** |
| 时效 | 最新 bar 时间戳 vs 当前时刻（`monitor/feed.py`） | 见 `SOLUTION.md` §四.1 |

原则和别处一致：**校验失败一律置空并标注，绝不用低分辨率数据顶替。**

三处刻意的设计：

**1. 量纲差异和读数分歧分开报。** 比对时这两件事必须分开：

- **比值 ≈ 100 或 10000** → 有一边量纲错了。这是 bug，有确定的修法，**修完两边完全一致**。
- **比值 ≈ 1 但差几个百分点** → 两个源对同一件事的测量确实不同（厂商把逐笔归并到
  分钟的边界处理不同，实测相对差最大 0.31%）。这是数据的性质，没有「正确答案」。

混在一起报会把唯一可修的那类埋进噪声里。上表三处陷阱全都是 100 倍或 10000 倍。

**2. 单位是反推的，不是配置的。** `amount / volume` 必须落在当根 bar 的价格量级上；
落在 100 倍开外，volume 记的就是手。这比信一个配置项可靠——量纲搞错不会报错，只会让
茅台的 VWAP 算成 135060 而不是 1350.60，然后每只票都显示为永远在均价下方。推不出来时
**不猜**：宁可不给 VWAP。

**3. 比对只出 note，不改数、不挑选。** 合并策略归 `CompositeMarketScanAdapter`
（主源整行为准，兜底只填空）。两件事混在一起会让「这个数用的是哪一路」变得不可追溯。

**没有分歧时也出一条 note。** 「比过了，一致」和「根本没比」在只报异常的设计里长得
一模一样——而后者正是这一层建起来之前的状态：`CompositeMarketScanAdapter` 一直在
合并两路，却从来没比过两路都有的字段。

## 六、价格口径

| 数据 | 口径 | 用途 |
|---|---|---|
| TickFlow 日线（默认 `forward`） | **比例前复权** | 均线、趋势、威科夫、支撑压力 |
| 新浪分钟线（`adjust=""`） | **不复权** | 买卖点、止损、目标——所有要挂单的价格 |

比例前复权锚定**最新**一根：不动今天，只重算历史。所以两条序列本来就共用今天的价格
尺度——2026-08-02 实测 400 只，前复权最新一根与不复权最新一根**无一例外完全相同**。

`TickFlowAdapter(adjust=...)` 接受 `none / forward / backward / forward_additive /
backward_additive`。**若改成 `backward`（后复权），历史保持原始价而今天被重算，
届时所有对外价位都必须换算**——`advice/engine.py:_session_alignment` 就是唯一
需要改的地方，乘法已经在正确的位置上了。

## 八、QMT：未开通，接口已留

QMT 是**执行侧**通道，第三方 API 是研究侧。即使接上 QMT，系统仍只用 `xtdata`、
从不用 `xttrader`——**不下单、不撤单、不接管账户**。

```text
盘前研究 / 盘后复盘   TickFlow(日线+行业) + AkShare(舆情/公告/龙虎榜) + 新浪(分钟线)
盘中执行             QMT / MiniQMT        ← adapters/qmt_xtdata.py，待开通
```

开通步骤：

1. 在跑这套系统的机器上安装并登录 `MiniQMT` 或 `QMT`
2. 确认本地 Python 能 `import xtquant.xtdata`
3. `ashare-ds qmt-health` —— 验证所需 `xtdata` 函数可见，并报告缺什么
4. 券商字段名不同时改 `examples/custom_mapping_profile.json`，
   归一层（`adapters/mapping.py`）在策略层看到数据之前解析别名

字段归一契约：每个规范字段接受一个别名列表，按序尝试，用第一个在原始 payload 里
出现的。缺必需字段抛归一错误；可选字段默认 `None`。**策略引擎从不直接读券商原始字段名。**

QMT 会补上：五档盘口（券商侧）、逐笔委托/成交、低延迟实时快照。
QMT **补不上**集合竞价撮合量与未匹配量——见 [`DECISIONS.md`](DECISIONS.md)。

## 九、仍然没测的一件事：盘中时效

非交易时段测不出盘中时效。**这一项对免费档和付费档都还是未知数。**

```bash
python3 scripts/source_audit.py --watch 600 --interval 3
ashare-ds intraday-check --symbols 600519.SH                    # 按档位自动选路
ashare-ds intraday-check --symbols 600519.SH --source sina      # 强制免费路
```

看两个数：

- **数据滞后中位** ≤ 3s → 该档位可支撑盘中判断
- **时间戳前进次数** 接近轮询次数 → 数据真在更新；若为 0，说明盘中不推进

要比的是**两条路的相对时效**：如果付费档与新浪相当，那就确认这 ¥99 买的是分钟历史
与配额而非实时性；如果付费档明显更新，实时这条线也该切过去。

2026-08-01 周六测得滞后 ≈ 9 万秒（即距上次收盘的自然时间），**该数字在非交易时段
无意义**，脚本会明确标注。

另一件没测的：**持续轮询是否触发新浪限流**。并发测试跑在非交易时段、总量 40 次请求；
一个交易日是 145 轮 × 50 只 ≈ 7000 次。设计里留了退路——指数退避 → 自动降频
（2→5→10 分钟）→ 挂起，每次降级推通知。批量快照接入后请求数从 `轮数 × 标的数`
降到 `轮数`，这个风险基本消失。
